# Davinci — Prior Art: backends, pass economics, and tool-facing IR

> [!NOTE]
> Third part of the prior-art survey ([part 1](./prior-art.md),
> [part 2](./prior-art-toolchains.md)), surveyed 2026-11-24. Part 1 covers
> MLIR's dialect design and LLVM's IR-contract debt; this page adds what
> they leave out: Cranelift and GCC, and the LLVM/MLIR lessons about
> **pass cost** and **tool-facing IR** (format, lint, LSP, type checking).
> Each entry states the practice, the failure history behind it, what
> Davinci already does (with the code that does it), and what is still owed.
> The owed items are collected in [the ledger at the end](#owed-ledger).

## Cranelift

**One IR, few levels, compile time as a product goal.** Cranelift has CLIF
(SSA with block parameters instead of φ), then VCode (machine instructions
with virtual registers), then bytes. It exists for JITs (Wasmtime) and the
rustc debug backend, so it trades peak code quality for compile speed and
says so. Functions are independent, so whole-module compilation parallelizes
across them without coordination.
_Davinci state:_ the same trade is the charter's priority order, and files
compile independently on per-worker arenas (`vize_l0::pool`). The
[walk budget](./plan/budgets.toml) `[traversal]` is meant to pin walks per
backend, but for DOM it cannot see the walks that matter (ledger O-1).
_Anti-lesson:_ Cranelift's original "meta" crate (encoding recipes, a
legalizer generated by a Python and later Rust DSL) was over-general and
slow. The 2020 `MachInst` backend and ISLE replaced it. An abstraction that
serves hypothetical targets costs real time on the actual ones.

**The ægraph mid-end: many passes become one.** Cranelift used to run GVN,
LICM, constant folding and peephole rewrites as separate passes, so it had a
pass-ordering problem. The ægraph mid-end
([RFC #27](https://github.com/bytecodealliance/rfcs/pull/27),
[EGRAPHS 2023 talk](https://cfallin.org/pubs/egraphs2023_aegraphs_slides.pdf),
[2026 retrospective](https://www.cfallin.org/blog/2026/04/09/aegraph))
replaces them with one structure. Rewrite rules apply when a node is
inserted, GVN falls out of hash-consing, LICM falls out of elaboration, and
the result is a few linear passes. Equality saturation is bounded, and the
graph is acyclic on purpose, to keep it linear. The prototype first cost
about 23% compile time over the old pipeline
([RFC thread](https://github.com/bytecodealliance/rfcs/pull/27)). The team
was willing to fund that only because the regalloc2 rewrite had just bought
about 20%, and later work brought it to net-negative.
_Import:_ pass composition is a data-structure decision, not only a
scheduling one. When several Davinci rewrites look at the same local shape
(static hoisting, constant attribute folding, cache-handler decisions), they
should be **rules applied at node construction in the one designated folding
pass** (part 1's LLVM rule: folding happens in exactly one pass per stage),
not N fusable passes over the same nodes. Fusion saves the walk; rules at
construction also save the re-match. The first application is ledger O-2:
the DOM emitter's asset-name collectors now ride the helper walk.
_Anti-lesson:_ the 23% is the warning. A general rewrite engine (worklists,
fixpoints, cost extraction) is slower than the hand-written passes it
replaces until it is engineered down. Davinci adopts it only where the
measured walk-plus-match cost is higher than the engine's cost.

**ISLE: declarative lowering rules with an overlap checker.** Lowering rules
are written in a term-rewriting DSL compiled to Rust match trees. The
compiler rejects overlapping rules with no priority, and the rules are the
input to verification (Crocus/VeriISLE, ASPLOS 2024).
_Import:_ the checker, not the DSL (part 1's ODS anti-lesson still holds).
Davinci's L2→L3 and L3→L4 lowerings are exhaustive `match`es on closed
enums with no `_` arms, which gives the overlap check for free from rustc.
Keep it that way.

**regalloc2 and the symbolic checker.** The register allocator ships with a
checker that symbolically re-executes the allocation and proves each use
reads the right value. Fuzzing runs the checker, not output diffs.
_Import:_ the stage verifiers already have this shape
(`vize_l2::verify::VerifyObserver` between passes in debug builds). The
extension is a **result checker for each decision pass**. Example: the L3
placement decisions are re-checked against the L2 facts they read, so a
fuzzer finds wrong decisions without a reference compiler.

**Incremental cache keyed by a stable IR hash.** Wasmtime caches compiled
functions keyed by a hash of the CLIF, with relocations and external names
parameterized out, so a renamed callee does not invalidate the caller.
_Davinci state:_ declaration fingerprints in `vize_l2::summary` (XXH3-128
per declaration, not per file) and salsa backdating in
`crates/vize_incremental/src/summary.rs` already do this for cross-file
facts. _Owed:_ the same parameterization for **emitted blocks**. A
template's L4 output should be keyed by its L2 content hash with the
component's import names and the hoisted-constant numbering factored out, so
an edit to one block does not re-emit an unchanged sibling block.

## GCC

**Three IRs, added late: GENERIC → GIMPLE → RTL.** Until GCC 4.0 (2005)
every optimization ran on RTL, a machine-level IR, because nothing else
existed. Tree-SSA added GIMPLE as a middle IR, and it took years. Then GIMPLE
was itself a reuse of the front-end `tree` type, a union-shaped node used
for types, declarations and expressions alike, with per-code flag bits
(`TREE_LANG_FLAG_0..6`) that mean different things for different codes. The
[tuples rewrite](https://gcc.gnu.org/wiki/tuples) (GCC 4.4, 2008) gave
GIMPLE its own compact statements and cut compiler memory by about 17% on
SPEC 2000 ([tutorial](https://www.airs.com/dnovillo/Papers/GIMPLE_Tuples_Tutorial.pdf),
preliminary numbers).
_Davinci state:_ every level has its own closed node types, and node sizes
are pinned by `const` size assertions (architecture guardrail 3). That is
the tuples lesson applied from day one.
_Anti-lesson:_ flag punning. A field whose meaning depends on the node kind
is GCC's `TREE_LANG_FLAG` again. Review question for L2/L3 changes: does any
bit or field change meaning by op kind? If so, split the type.

**Pass manager: `gate`, properties, and deferred TODOs.** A GCC pass
(`opt_pass`) has a `gate()` that decides, per function, whether it runs at
all. It has `properties_required/provided/destroyed` (`PROP_cfg`,
`PROP_ssa`, …), which form a typestate on the IR. And it has
`todo_flags_finish` (`TODO_update_ssa`, `TODO_cleanup_cfg`): cleanups the
pass needs but does not run itself. The manager merges pending TODOs, so
three passes that each dirty the CFG pay for one cleanup.
_Davinci state:_ `gate` exists as artifact-selected plans. The L2 transform
plan is chosen from `LoweringFeatures` bits published during lowering
(`davinci/vize_l1_to_l2/src/dialect/vue/pass/plan.rs`), and all 32 plans
are `static`, so a file with no slots never enters `v-slot`. The DOM build
path does not use that table: it repeats the same three gates by hand in
`davinci/vize_l1_to_l2/src/pass/dom.rs` (ledger O-3). The typestate exists
as `Raw`/`Canonical` (`vize_l0::pass::canonical`).
_Owed:_ deferred, coalesced cleanup. When two fused passes each need the
same follow-up (re-numbering hoists, rebuilding a side table), the manager
should run it once at the group's end, declared as data on `PassDesc` like
`preserved`.

**WHOPR: summaries decide, bodies transform in parallel.** GCC's
partitioned LTO ([design overview](https://gcc.gnu.org/onlinedocs/gccint/LTO-Overview.html))
has three stages. LGEN writes IR plus a local summary for each unit. WPA
reads **only the summaries**, sequentially, and makes the whole-program
decisions. LTRANS applies the decisions to partitions in parallel. The whole
program is never in memory at once.
_Import — the model for project-level checking:_ cross-SFC questions (prop
and emit types, component registration, auto-imports) are WPA questions.
They should read per-SFC summary facets (`vize_l2::summary::SfcSummary`),
never another file's L2 body. Per-file type checking and lint are then
LTRANS: parallel, and limited by the largest file, not the project.

**Delayed folding in the C++ front end.** GCC folded constants while
parsing (`fold()` from the front end), so the tree no longer matched the
source. That broke diagnostics (warnings named expressions the user never
wrote) and `constexpr` evaluation. The C++ front end moved to delayed
folding (`cp_fold`, GCC 7) to keep source fidelity until the middle end.
_Davinci state:_ the same rule, stated twice. L1 is lossless, and part 1's
LLVM import puts folding in exactly one designated pass per stage. For
tools it is decisive: the formatter, lint autofix and LSP read the unfolded
form, so folding must never move into L1 construction or L1→L2 lowering
"because it is cheaper there".

**Diagnostics were retrofitted.** GCC tracked lines only, added columns
later, ranges and fix-it hints in GCC 6, and JSON and SARIF output in GCC 9
and 13. Each step touched every front end.
_Davinci state:_ spans are two `u32`s from L0, and `products.fixes` makes
fix-its one mechanism that edits L1 spans. No retrofit is owed.

**No library, no IDE.** GCC had no reusable, error-recovering parser API and
for political reasons resisted exporting its IR. Its plugin API exposes
internal headers, so plugins break on every release. The 2003 compile server
(incremental compilation for IDEs) was abandoned. IDE support for C and C++
came from Clang and clangd instead.
_Davinci state:_ this is the strategic lesson the north star is built on,
and it is the least finished part. The gates say every product reads the
same levels and "never parses on its own" (`products.lsp`). Today the
products still parse separately: the type checker's template codegen parses
with the legacy `vize_armature` parser
(`crates/vize_canon/src/batch/virtual_project/vue_codegen/template.rs`),
`vize_maestro` refers to `vize_armature` in 37 places, and the per-block
resident queries are behind `experimental-resident-*` features that are not
in the default set (ledger O-5, O-6).

## LLVM and MLIR: pass cost

**Fixpoints are a compile-time tax.** InstCombine ran to a fixpoint. Making
it a single iteration cut about 4% of CTMark compile time with almost no
code-quality loss ([Red Hat, 2023](https://developers.redhat.com/articles/2023/12/07/how-single-iteration-instcombine-improves-llvm-compile-time)).
The 2024 RFC to [skip transform passes that just ran](https://discourse.llvm.org/t/rfc-pipeline-avoid-running-transform-passes-that-have-just-been-run/82467)
saves another 0.5–0.8%: if nothing changed since a pass last ran, running
it again is wasted.
_Import:_ no optional pass in a product pipeline iterates to a fixpoint. A
pass that wants one is a barrier with a stated iteration bound, and the
bound is in its `PassDesc` docs. A pass that runs twice in one pipeline
(today none does) needs a "changed since" bit so the second run can be
skipped.

**The compile-time tracker.** LLVM got 5–10% slower per release until
[llvm-compile-time-tracker](https://github.com/nikic/llvm-compile-time-tracker)
measured instructions retired per commit. Making regressions visible per
commit, rather than per release, reversed the trend.
_Davinci state:_ `level-instruction-counts.yml` gates instruction ceilings
in the merge queue on the shipped release profile. Every PR reports a
measurement table.

**The pass manager is load-bearing; replace it early or never.** LLVM's new
pass manager started in 2013, became the default in LLVM 13 (2021), and the
legacy one lingered in codegen after that. The cause was the stale-analysis
bugs part 1 names.
_Davinci state:_ the pass manager (`vize_l0::pass`) existed before the
passes. Plans are `const` data and fusion groups are `const`-pinned, so a
grouping regression is a compile error. But a group is a plan, not an
execution: `run_pipeline_remarked` calls the step once per pass, so two
passes in one group still walk twice unless the caller fuses the bodies by
hand, as `pass/template.rs` does for `hoist-static` and
`template-complexity` (ledger O-4).

**MLIR: uniquing and generic storage cost throughput.** MLIR keeps types
and attributes uniqued in a shared `MLIRContext`, so multithreaded pipelines
contend on its locks. It also stored every op's inherent data in a uniqued
attribute dictionary until op _properties_ (2023,
[commit](https://lists.llvm.org/pipermail/mlir-commits/2023-May/011555.html))
moved it inline. The split is still unfinished in 2025
([discussion](https://discourse.llvm.org/t/non-attribute-properties-and-the-inherent-discardable-attribute-split-what-needs-doing/87782)).
_Davinci state:_ allocation is a per-file arena, with no global interner on
the hot path. Op data is typed fields, not a dictionary.
_Anti-lesson:_ never add a process-wide interner or registry to a hot level
"for deduplication". Deduplicate inside the file's arena.

**MLIR: `IsolatedFromAbove` is what makes nesting parallel.** MLIR's pass
manager runs a nested pipeline on many ops at once only when those ops cannot
see values defined outside them. Isolation is the parallelism and caching
contract.
_Import:_ an SFC block is isolated from above, except for one declared
interface: the script's binding table, which the template reads. That makes
per-block caching sound. The template's L2 depends on the script only
through binding _kinds_, so a script edit that keeps every kind (a function
body change) must not re-lower the template.

## Tool-facing IR: Clang and clangd

**The preamble.** clangd parses the header prefix of a file once, with
`SkipFunctionBodies`, and reuses it until the prefix or the compile command
changes. Only the main-file suffix is reparsed per keystroke. The source
calls it the most important optimization in clangd
([`Preamble.h`](https://clang.llvm.org/extra/doxygen/Preamble_8h_source.html)).
Validity is pull-based: it is checked only when the main file is used.
_Import:_ for an SFC, the stable prefix is "every block but the edited one",
and the body to skip is script bodies when only signatures are needed. The
cross-file summary needs `defineProps`/`defineEmits` and exported types, not
function bodies.

**clang-format is not built on the AST.** It formats from tokens and
"unwrapped lines", so it works on code that does not parse and never pays for
semantic analysis.
_Davinci state:_ `products.formatter` is "Glyph formats from L1 only", the
same decision. The code survey reports that Glyph reads the L1 container
split and then scans template bytes itself; that is to be confirmed under
ledger O-5.

**No mid-level IR, then ClangIR.** Clang lowers its AST straight to LLVM IR.
High-level analyses (lifetime, C++ idioms) had no place to live, so ClangIR
(an MLIR dialect) is being added a decade later. Swift SIL, Rust MIR and
Flang FIR are the same correction.
_Davinci state:_ L2 and L3 are that mid-level IR, and lint semantic rules
run on L2.

## Where the native DOM route spends its instructions

The surveys above say what to avoid. This section says where the levels cost
time today, measured on 2026-11-24 on `main` at `0376402504`: retired
instructions per stage on the ladder fixture `large.vue`, default options,
read from the macOS process counter on arm64 in the `ci-opt` profile
(repeatable to about 0.1%). It is a local probe, not the gated callgrind
measure.

| Stage               | Native | Legacy |
| ------------------- | -----: | -----: |
| Parse               |   336k |   908k |
| Lowering, transform |   766k |   119k |
| Emit, codegen       | 1,482k |   851k |
| Total               | 2,585k | 1,879k |

- **The front is at parity.** L1 parses 2.7 times faster than the legacy
  parser, and lowering spends what that saves. Parse plus lowering is 1.10M on
  one side and 1.03M on the other.
- **The whole deficit is the L4 emitter**: 1.74 times the legacy code
  generator on this template.
- **Walk count is not where the time goes.** O-2 took a production compile
  from five template walks to three and measured −0.5% to −2.8% of the emit
  stage. A walk over a few hundred ops costs little; what a visit does costs
  a lot.
- **The emitter re-derived what it had just written.** A sampling profile put
  32% of the emit stage in one function that scans the generated module for
  the first call of a helper alias, once per ordering question (O-11). About
  19% more went to spelling event handler keys, four or more times per
  listener, one character at a time (O-12). Both are LLVM's "derivable and
  cached, never both" rule in part 1, broken in the cheap direction: derived
  again each time instead of cached.
- **The budget has no row for any of this.** `instruction-budgets.toml` has no
  native-stage row on the ladder fixtures, and `atelier_dom_compile_*`
  measures the public entry, which also runs the legacy parser because it
  returns the legacy tree (O-13).

## Owed ledger

Owed items from this survey. Each one lands only with measurements under
the [no-regression rule](./charter.md).

- **O-1 (open): Make the DOM walk budget measure real walks.** `DomEmitBudget`
  reports `emit_walks: 1` as a constant
  (`davinci/vize_l4/src/framework/vue/dom/budget.rs`), and the three fact passes
  run outside the observer (`pass/dom.rs`). The emitter also walks for
  static-cache admission, helper order and, until O-2, asset names. Count every
  `PageWalk` and gate the count. _Source:_ LLVM compile-time tracker.
- **O-2 (this change): Collect preamble asset names in the helper walk.**
  `component::collect_names` and `directive::collect_names` each walked the
  whole template before emission. Both lists now come out of
  `helper_preference::prefer_helpers`, checked against the old walks as test
  oracles. A `<script setup>` production compile (inline, static hoisting on)
  walked the L2 template five times: `hoist-static`, helper order, component
  names, directive names, emit. It now walks three times. Slots and `v-model`
  each add one more on both sides. Measured, the gain is small: −0.5% to
  −2.8% of the emit stage. _Source:_ Cranelift ægraph.
- **O-3 (open): One gate table for every route.** Run the DOM fact passes from
  the `static` plan table, so a new pass or feature bit cannot be gated on one
  route and missed on the other. Needs proof of zero added instructions.
  _Source:_ GCC `gate`.
- **O-4 (open): The path to one DOM walk.** Three walks remain after O-2, and
  `budgets.toml` targets one (`dom_walks_max = 1`).
  - Fact passes: `v-slot`, `v-model` and `hoist-static` are three shaped
    recursions, each with its own state (owner context, a scope environment,
    a post-order lattice). `vize_l2::analysis::template` already composes
    `hoist-static` with `template-complexity` in one walk, behind
    `composed-template-analysis`. Extend that composed form to the two
    mandatory fact passes, then let the manager drive it for any group.
  - Static facts: the architecture says cheap facts are synthesized during
    lowering. `hoist-static` is post-order and local, so it is the candidate
    to be published by L1→L2 lowering, as text, `v-if` and `v-for` facts
    already are.
  - Helper order: the helper walk exists because import order is pinned to
    the legacy transform's visit order, and the emit walk skips subtrees. It
    can go only if that order becomes a published fact or the emit walk can
    assign the same visit keys. Open research; it depends on target options
    and on slot facts.

  _Source:_ Cranelift ægraph, MLIR.

- **O-5 (open): One front end per revision in the LSP.** The surveys counted
  up to four template front ends per document revision (legacy parser, L1→L2
  lowering, the formatter's scanner, an L2→legacy tree rebuild) and repeated
  script parses. Make the per-block `l1_block`/`l2_page` queries the default and
  move features onto them one at a time. Overlaps #13539 and #13516; coordinate
  before starting. _Source:_ clangd preamble, GCC "no library".
- **O-6 (open): One virtual-TypeScript projection.** Canon, Maestro and the
  type-aware lint rules each generate virtual TS. The `vize_l4` projection is
  the intended single source (`products.typechecker`). _Source:_ Clang tooling.
- **O-7 (open): Summaries decide project questions.** Audit cross-file lint
  and type checking for reads of another file's body instead of its `SfcSummary`
  facets. _Source:_ GCC WHOPR.
- **O-8 (open): Kind-preserving script edits keep the template.** Key template
  L2 on the script's binding kinds, not its text. _Source:_ MLIR
  `IsolatedFromAbove`, Cranelift cache.
- **O-9 (open): Coalesced follow-ups on `PassDesc`.** Declare shared cleanups
  as data so a group runs each once. Only worth doing after O-4. _Source:_ GCC
  TODO flags.

- **O-10 (open): SSR stops at L4 when L4 emitted.**
  `compile_ssr_on_lane_with_runtime` (`crates/vize_atelier_ssr/src/compile.rs`)
  parses with the legacy parser, lets `select_ssr_lane` parse again in L1,
  lower and emit, and then always runs the legacy transform, even after
  `SsrL4Selection::Emitted`. The SFC caller drops the transformed tree and
  keeps only the error list and the code.

  The transform cannot be skipped yet, because it is still the lane's
  diagnostic producer. An experiment on 2026-11-24 logged every SSR compile in
  the `vize_atelier_ssr` and `vize_atelier_sfc` suites and the fix-history
  corpus: of 3,826 compiles that L4 emitted, 35 (10 distinct inputs) carried a
  fatal error that only the legacy transform reported. The classes were
  `InvalidExpression` (slot parameters, TypeScript in a JavaScript template),
  `VModelArgOnElement`, `VModelOnScope`, `VSlotMixedSlotUsage`,
  `VSlotUnexpectedDirectiveOnSlotOutlet` and `ExtendPoint` (patterned
  templates). The DOM route gets the slot and model errors from the L2
  `v-slot` and `v-model` passes; the SSR L4 lane does not run them.

  The order of work follows from that. First the SSR lane runs the same L2
  mandatory passes and reports those classes itself, with identical codes and
  spans. Then the differential harness asserts that an emitted compile has no
  transform error. Then the transform is skipped behind a default-off flag,
  checked on the full matrix and the fix-history corpus. Last, the frozen-slot
  facts come from L1, so the legacy parse goes too. This is SIL's lesson in
  part 2: diagnostics attach to mandatory passes on one path, not to a second
  pipeline kept alive beside the first. _Source:_ GCC `gate`, LLVM "skip
  passes that just ran", Swift SIL.

- **O-11 (in review): Order helper imports from one lexical scan.** The
  import list is ordered by where each alias is first called in the generated
  module. The comparator rescanned the module per alias unless it was over
  64 KiB; the shared scan had only ever been measured on one 71 KiB fixture
  (#10102). Every module now uses the shared scan, lazily, with the per-alias
  scans as a debug oracle. Local release-profile probe: emit −22% on
  `large.vue`, equal elsewhere. The better end state records each helper's
  first call when it is written, so nothing is scanned. _Source:_ LLVM "one
  encoding", Cranelift ægraph.
- **O-12 (in review, part): Spell an event handler key once.**
  `event_key_for` runs for patch flags, for the duplicate-listener check and
  for the emit, and built its result through `camelize` and `capitalize` one
  character at a time. Those two helpers now copy unchanged runs whole (emit
  −38% on `large.vue` together with O-11, −10% on `stress-wide`). Still owed:
  the key as a fact computed once per listener, in lowering or in a per-emit
  table. _Source:_ LLVM "derivable and cached".
- **O-13 (open): Give the native route stage rows.** Add L1 parse, lowering,
  L2 passes and L4 emit rows for the ladder fixtures to the instruction
  harness, and a row for the SFC fast path that does not run the legacy
  parser. Without them a native-stage regression is invisible until it shows
  in an end-to-end ratio. After O-11 and O-12 the emit profile's next entries
  are buffer pushes and `memmove` (about 18%) and temporary allocations
  (about 5%). _Source:_ LLVM compile-time tracker.

O-5 to O-8 come from a code survey on 2026-11-24 that counted call sites and
took no timings. Each needs a measurement before it is scheduled.
