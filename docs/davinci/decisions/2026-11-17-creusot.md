# Creusot replaces Kani as the formal verification tool

The maintainer decided on 2026-11-17 to stop using Kani and to verify the
Davinci laws with [Creusot](https://github.com/creusot-rs/creusot), properly
and not as a token effort. On 2026-11-18 the maintainer kept Kani for one
area: the L3 incremental update machine (see
[Kani stays for the incremental update machine](#kani-stays-for-the-incremental-update-machine)).
This record states why, how the tool is pinned and
run, what it cannot express in our code, and how those parts are verified
instead. It changes the tool behind the
[`formal.rust-only`](../completion-gates.md) gate
([#10825](https://github.com/ubugeeei-prod/vize/issues/10825)), not the laws:
every law the earlier records moved out of Lean
([lattice](./2026-10-13-8840-l3-lattice-laws-kani.md),
[HTML content model](./2026-10-13-8840-html-content-model-kani.md),
[L3 reference](./2026-11-03-10825-l3-reference-laws-kani.md)) keeps its
statement, and each Kani harness outside the incremental update machine is
replaced by a Creusot proof of the same law.
The [inventory](./2026-11-17-creusot-inventory.md) lists every harness, its
bound and its replacement.

## Why

Kani is a bounded model checker. Every harness states a bound: three ops and
one edge for the scheduling laws, fixed tree shapes for the incremental update
machine, four frames and two revealed ancestors for the content-model walk. A
bound is a sample, not a proof. The incremental laws show where that ends:
CBMC could not bound a symbolic tree even at width two (the smallest
`retain_ok` harness ran past 900 s at 2.9 GB), so
[#11631](https://github.com/ubugeeei-prod/vize/issues/11631) settled for fixed
shapes with symbolic values.

Creusot is a deductive verifier. A contract quantifies over every input, so a
proof covers trees of any depth, programs of any size and stacks of any length.

- **Unbounded proofs.** `requires`/`ensures` contracts, loop invariants and
  variants prove the general statement the Lean theorems made, not an
  instance of it.
- **Contracts on the shipped functions.** The contract sits on the function the
  product runs. Callers are proved against it, and Why3 checks the body
  against it.
- **Specs document the laws.** A law is a Pearlite formula next to the code it
  constrains, and `cargo creusot doc` renders it. A Kani harness is a test
  driver that someone has to read backwards.

## How Creusot is pinned and kept out of the product build

Creusot ships as a rustc driver tied to one nightly compiler, so it never
touches the stable 1.100 build.

- **Toolchain.** [`tools/nix/creusot/flake.nix`](../../../tools/nix/creusot/flake.nix)
  is a flake of its own. It pins Creusot `v0.14.0` (commit `65349025`), with
  its `nightly-2026-08-03` compiler, Why3, why3find and the solvers, through
  its own `flake.lock`. The product flake, its lock, `rust-toolchain.toml` and
  every product workflow are unchanged. Run it with
  `nix develop path:./tools/nix/creusot`.
- **Proof crate.** [`tests/formal/creusot`](../../../tests/formal/creusot) is a
  separate Cargo workspace with its own lock. It depends on
  `creusot-std =0.14.0`, which the toolchain wrapper patches to the copy
  shipped with the pinned Creusot. Each member's `[lib] path` is a `creusot.rs` root next to
  the kernel it proves (`davinci/vize_l3/src/lattice/creusot.rs`), the way
  `kani.rs` sits next to it. The root is in no product module tree and
  declares the shipped modules by ordinary module discovery (the repository
  refuses `#[path]`), so the proofs are about the exact source the product
  compiles.
- **Zero-cost annotations.** Kernel contracts are written
  `#[cfg_attr(creusot, ensures(...))]`, and logic functions are
  `#[cfg(creusot)]`. Only the Creusot driver sets `cfg(creusot)`. Elsewhere
  rustc removes the attribute during cfg expansion, before name resolution, so
  the product crates do not depend on `creusot-std`, and they see no new
  item, no proc macro and no extra token. `cfg(creusot)` is declared in the
  workspace `check-cfg` list, so clippy and `unexpected_cfgs` stay clean.
  `no_std` and arena code compile byte for byte as before. The instruction
  ceilings and the release binary size check this on every PR that adds
  annotations (see [Performance](#performance)).

## Solvers, proof storage and CI

`cargo creusot` translates the crate to Coma, and
[why3find](https://git.frama-c.com/pub/why3find) discharges every goal with
the solvers the pinned flake provides: Alt-Ergo 2.4.3, Z3 5.1.0, CVC5 1.4.1
and CVC4 1.8. The flake uses Creusot's `free` bundle. Alt-Ergo 2.4.3 is open
source, while the default bundle's Alt-Ergo 2.6 is under OCamlPro's
non-commercial licence.

why3find stores one proof certificate per module (`proof.json`): for each goal,
the solver or tactic that proved it and the time it took. The certificates are
committed under `tests/formal/creusot/verif/`. The generated Coma is not
committed, because CI regenerates it from source.

[`davinci-creusot.yml`](../../../.github/workflows/davinci-creusot.yml) builds
the pinned toolchain and runs `cargo creusot --replay`. Replay regenerates the
Coma from the current source and checks every goal against its certificate. It
never searches for new proofs, so a goal that changed, or one without a
certificate, fails the job. The run is deterministic: the toolchain, solvers
and certificates are all pinned. It is also bounded in time: each replayed
goal keeps the per-goal limit in `why3find.json`, and the job has a hard
timeout. A contributor who changes a kernel or a contract runs `cargo creusot`
locally, which searches for proofs and rewrites the certificates, and commits
the result.

The first CI run had no cache, so it built the toolchain from source: Z3,
CVC5, CVC4, Why3, why3find and Creusot, 283 derivations. On the
`blacksmith-32vcpu-ubuntu-2404` runner
([run 44292007681](https://github.com/ubugeeei-prod/vize/actions/runs/44292007681),
2026-11-18), the job took 12 min 10 s. The toolchain build took 10 min 54 s
and the replay took 51 s (`Proved (9 files)`). That fits the job's 60-minute timeout.
Later runs restore the Nix store from `cache-nix-action`, keyed on the subflake
lock, and skip the source build until the pin changes. The same build took
55 min locally on a loaded macOS machine.

The trusted base is Creusot's translation, Why3 with its solvers, and the
`creusot-std` specifications of the standard library functions the kernels
call. Our own code adds no `#[trusted]` item unless it is listed in the
[inventory](./2026-11-17-creusot-inventory.md) with its reason. A tooling test
holds the source to that list.

## What Creusot cannot express here, and what verifies it instead

Creusot verifies safe Rust whose standard-library calls have specifications.
The first proofs found where that ends in our code, besides what was known
beforehand:

- **Arena-backed code** (`bumpalo` and the `oxc` allocators): lifetimes
  tied to an arena, `Box<'a, T>` and arena `Vec`s have no Creusot model.
- **Raw pointers and `unsafe`**: Creusot's permission-based pointer reasoning
  needs ghost code threaded through every use, which the product cannot
  carry.
- **`dyn Trait`** and other trait objects: they cannot carry a contract.
- **Standard-library calls without a specification.** Creusot gives such a
  call an impossible precondition, so a goal that reaches it never proves.
  This covers formatting (`fmt::Write`), `str::as_bytes` and `str::split`,
  `<[T]>::split_first`, and the iterator adaptors `find`, `find_map`,
  `position`, `any`, `all` and `try_fold`. `Enumerate` has no
  `DoubleEndedIteratorSpec`, so `iter().enumerate().rev()` is rejected too.
- **Array and slice patterns** (`let [a, b, c, d] = codes`,
  `matches!(codes, [None, None, None, None])`). Creusot 0.14 stops with an
  internal error on the `ConstantIndex` projection they lower to. The L3
  reference reads such arrays by constant index instead.
- **String literals in specifications.** Pearlite rejects a `"..."` literal;
  a `const` item of type `&str` works in both code and contracts, so the L3
  reference names its validator codes (`L3V001` ...) as constants.
- **Casts of an enum to its discriminant** (`self as u8`). Creusot 0.14
  translates the cast to an unconstrained value. A kernel that needs the
  number matches on the variants instead. `ReactivityClass::rank` keeps the
  cast in the product and uses the match only under `cfg(creusot)`, so the
  product compiles to the same code as before the proofs; `tests/lattice.rs`
  pins each discriminant to its chain position.
- **Compiler derives over discriminants.** Derived `PartialOrd`, `Ord`, `Hash`
  and `Debug` read the discriminant through intrinsics, so they cannot meet
  the trait contracts. `Clone` and `PartialEq` use Creusot's own derives, which
  it does verify.
- **Recursive types through `Vec`** (the incremental machine's trees), and
  mutually recursive logic functions. Creusot rejects a type that recurses
  through `Vec` unless a trusted `extern_spec!` declares `Vec` positive in its
  parameter. A tree law is stated with a depth argument instead, and proved by
  induction on it. The incremental update machine stays on Kani for this
  reason (see below).

Those parts are verified in one of two ways, and the inventory says which for
each law:

1. **A verified pure model with a refinement link.** The law is proved about a
   dependency-free kernel. Where the kernel is the shipped code (the lattice
   evaluator, the content-model walk), the proof is about the product itself.
   Where it is a reference (the L3 reference machine), a Rust oracle checks
   the producer against the reference on every committed fixture. The checker
   corpus, the schedule-contract differential and the incremental witnesses
   already do this.
2. **A Rust oracle**: an exhaustive or differential Rust test, named in the
   inventory, for a statement that is outside what Creusot can express.

No law is marked proved unless Why3 has discharged every goal. A kernel item
that is not part of a law and that Creusot cannot verify is not `#[trusted]`
into scope. It is compiled out of the proof crate with `#[cfg(not(creusot))]`
(the folio spellings `as_str`/`from_str`) or
`#[cfg_attr(not(creusot), derive(...))]` (the discriminant derives), so it is
visibly outside the proof, and the inventory names the Rust oracle that covers
it. Every remaining item of an included kernel has all its goals proved,
including the safety goals (no panic, no overflow) of functions without a
contract.

## Kani stays for the incremental update machine

The maintainer decided on 2026-11-18 that Kani remains the verifier of the L3
reference incremental update machine
(`tests/davinci_test_support/src/l3_reference/incremental.rs`, harnesses in
`incremental_proofs.rs`,
[#11631](https://github.com/ubugeeei-prod/vize/issues/11631)). Creusot covers
what it proves without trust today, starting with the lattice laws, and the
incremental-tree proofs stay on Kani.

- **No trusted declarations in Creusot proofs.** The machine's `View` and
  `Node` trees recurse through `Vec`. Creusot 0.14 accepts that only with
  `extern_spec! { #[trusted(positive(T))] type Vec<T>; }`, a trusted
  declaration about the standard library. The Creusot proofs admit no trusted
  item, so that declaration is not added.
- **An arena rewrite is not worth it now.** Storing the trees as index-linked
  nodes in one flat arena would avoid the recursive type, but it rewrites the
  reference machine, its Kani harnesses and its witnesses for a proof the
  bounded harnesses already sample. It is not done now.

A draft Creusot port of the machine discharged 44 of its 45 goals before the
decision, using the trusted `Vec` declaration. It is not committed. The nine
incremental harnesses, their bound and `davinci-kani.yml` stay as they are,
and the [inventory](./2026-11-17-creusot-inventory.md) marks their rows
`kani`. Revisiting this needs a new maintainer decision.

## Performance

The annotations do not reach the product build. Each PR that annotates a
shipped kernel proves it on the crate's code: the LLVM IR of the crate at
`opt-level=3` with one codegen unit must be identical between base and head,
and the instruction ceilings (`level-instruction-counts.yml`) must hold. For
`vize_l3` in the first PR, the IR is identical except for one `!srcloc`
constant. That constant is the source position Rust records on an inline-asm
`black_box` for its diagnostics: the annotations add bytes to the crate's
source map, so the position shifts. It emits no code.

## Order of work

1. This record, the pinned toolchain, the proof crate and the workflow, with
   the value-axis laws (`ReactivityClass::join`) as the first proofs.
2. Proofs by area: the scheduling contract and the C-23 checker, the rest of
   the lattice, and the HTML content-model kernel. Then the most valuable laws
   no harness states yet, where they are tractable: lossless L1 render equals
   source, span monotonicity, and lowering totality. The L3 incremental update
   machine is not ported; it stays on Kani.
3. Kani is not removed. It remains the verifier of the incremental update
   machine, so `davinci-kani.yml`, the Kani toolchain and the incremental
   harnesses stay. The Kani harnesses of every other area are deleted only when
   each of their laws is proved in Creusot or covered by a documented oracle.
   The `formal.rust-only` gate in [completion-gates.md](../completion-gates.md)
   already names Creusot proofs, Kani harnesses and Rust oracles (maintainer
   decision 2026-11-18), so deleting those harnesses does not change it.
