# One fix type: owned span edits, applied through versioned L1 edit sets

Tracked in [#6876](https://github.com/ubugeeei-prod/vize/issues/6876)
(`products.fixes`: "Diagnostic fixes, code actions and lint autofixes are one
mechanism that edits L1 spans"). This record is slice FX1. It builds on the
provider in [versioned span edits](./2026-10-02-versioned-span-edits.md) and
fixes what the products converge on. FX2 to FX5 implement it.

## What exists

| Piece                                    | Where                                                                | What it does                                                                                                                             |
| ---------------------------------------- | -------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| `Fix { message, edits }`, `TextEdit`     | `vize_patina::diagnostic::types`                                     | owned edits a rule attaches to a diagnostic; serialized as `{ "message", "edits": [{ "start", "end", "new_text" }] }`                    |
| `Fix::apply`                             | same                                                                 | applies one fix: sorts by descending start and splices every edit, overlapping or not                                                    |
| `apply_lint_fixes` (twice)               | `vize/src/commands/lint/fix.rs`, `vize_vitrine/src/napi/lint_fix.rs` | applies all fixes of a result: drops invalid ranges, sorts by `(start, end)`, keeps the first of overlapping edits, splices from the end |
| `VersionedSource`, `SpanEdit`, `EditSet` | `vize_l1::edit`                                                      | checked edits bound to a host snapshot key, client version and the exact parsed buffer; one-pass application                             |
| `workspace_edit`                         | `vize_maestro/src/ide/code_action/versioned_lint_edits.rs`           | binds Patina `TextEdit`s to the open document and publishes them through an `EditSet`                                                    |

There are three appliers with two different overlap policies, and only Maestro
checks a document version. Canon has a private `TextEdit` for declaration
paths that never leaves the checker.

## Decision

1. **One owned edit type, in L0.** `TextEdit` (authored byte span plus
   replacement) and `Fix` (message plus edits) move to `vize_l0::diag`.
   Patina re-exports them under their current paths. The fields, the serde
   derive and therefore the CLI, NAPI, WASM and SARIF JSON stay byte-identical.
   Every product that reports a fix (lint rules, Canon quick fixes, compiler
   diagnostics, Glyph rewrites that change meaning) emits this type. Offsets
   address the exact input the producer read, never a decoded or virtual
   coordinate. Projections from virtual code map back before a fix is emitted.
2. **One application authority, in L1.** Edits are validated and applied only
   as a `vize_l1::edit::EditSet` bound to a `VersionedSource`. The host supplies
   the key and version. The CLI and NAPI fix loop apply each pass in the same
   call, on the buffer that pass linted, so that buffer is the snapshot
   identity. Maestro keeps `(uri, revision)` plus the client version. No
   product splices strings itself.
3. **One selection policy.** `vize_l1::edit` gains the selector the two
   `apply_lint_fixes` copies implement today. It drops reversed, out-of-range
   and non-UTF-8-boundary edits, orders by `(start, end)` with ties in
   diagnostic order, and keeps the first of any overlapping edits. To keep
   that output exact, `EditSet` accepts consecutive insertions at one offset
   and applies them in supplied order, which is what the splice-from-the-end
   loop produces today. `Fix::apply` (one fix, used by tests and the
   fix-history observers) goes through the same selector. A fix whose own
   edits overlap is a rule bug; the history corpus is the check that none
   exists before the policy is shared.
4. **Version travels with the snapshot, not the diagnostic.** `LintResult`
   and `Fix` stay version-free, because the same result is serialized for
   hosts that have no version. A host binds the version when it applies or
   publishes. A stale version, a foreign buffer or a different key is an
   explicit `EditError`, and the host drops the action.

## Order and proof

- **FX2:** move the types into `vize_l0::diag`, add the selector, and route
  `Fix::apply`, the CLI and NAPI through `EditSet`. Proof: CLI and NAPI JSON
  byte-identical on the Patina fixtures and lint differential, fixed output
  byte-identical on the linter fix-history corpus, release binary size not
  larger.
- **FX3:** Maestro's template, plugin and JSX lint actions all use
  `workspace_edit`; the unversioned `WorkspaceEdit::changes` path goes away.
- **FX4:** Canon and compiler quick fixes emit the L0 type.
- **FX5:** Glyph rewrites that change meaning become lint autofixes.

The gate closes when every fix-producing product emits the L0 type and every
applier goes through `EditSet`.
