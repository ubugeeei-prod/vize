# Physical native runtime assets and rename ownership

Issue: [#8010](https://github.com/ubugeeei-prod/vize/issues/8010).

The original project/root boundary admits an actual configured TypeScript
distribution when its regular files are copied inside the writable project,
outside `node_modules`. This is a physical ownership problem: a project member,
plain Canon identity mapping, or explicit `isDefaultLibrary: false` does not
establish an authored writable source. The published native 7.0.2 API also
reports false for an actual native declaration explicitly rooted under `noLib`.

The bounded source change requires a retained SFC compiler projection before
admitting each native rename target. Hosts and dependencies retain their source
maps; materialized/catalog entries require generated SFC mappings rather than
plain `AuthoredIdentity` entries. Every unknown endpoint refuses the entire
packet before coordinate mapping or filtering. The same request-local scope is
carried through canonical rewriting and the caller's structural supplement,
then checks every final container and both URIs of resource renames. Refusal is
distinct from an unavailable route, so structural fallback cannot return only
the safe-looking portion. Older block projections inspect their whole raw
packet against the exact returned virtual document before mapping.

Generated request leaves cannot be symlinks, and Unix hardlinks cannot supply a
generated or authored SFC owner. Legitimate ancestor spelling such as `/tmp`
remains supported. Final path memoization uses current physical identity, so
retargeting an authored link cannot reuse an old in-root admission. This adds
no native metadata RPC, process, protocol, retained Program-role cache, or
pipeline stage. A false metadata role never becomes writable authorship.

preserves the original Toggle/App and changes only `const emit` to `let emit`
for the independent unsafe case. The actual retained H producer
`fd6241bf8ea5466794cc955138a59a9b75a8aac2`, a version-only child of signed
`177933f33e75af1f696fdc468665e7850025d28b`, returns the same eight wrong edits
for original const, mutable let, and the noLib rooted-distribution variant:
six DOM entries, one Webworker entry, and the Toggle string. Both original
diagnostic arrays are empty. Its 109 physically copied files total 27,438,862
bytes; every original and copied asset hash remains unchanged and no returned

are historical reproduction only, with no current-source or publication credit.

The new genuine-source CLI controls copy the actual self-contained distribution
as regular bytes, with a 40 MiB preparation bound, and preserve complete before
and after hashes. Five unsafe sessions cover LF/CRLF, default/noLib roots, and a
Unix relay outside the writable root executing the copied native binary inside
it. Fifteen complete read-only reference vectors stay available while all
fifteen full unsafe rename results must be null. Two positive sessions retain
the independently authored flip-two and imported-alias-three edit packets,
apply only the SFC file to disk, require version-2 empty diagnostics, and restore
the independent original with empty diagnostics. A user `lib.custom.d.ts` with
a no-default-lib header in the copied directory stays byte-exact; these are
Vue-local alias positives, not declaration-exporter write qualification.

Existing original scope/refusal and named-type/component/event/model/package
controls remain required without expectation weakening. Hosted exact-source
Actions must compile and execute the new and inherited controls, native
cancellation/lifecycle checks and unchanged performance ceilings before source
qualification. Protected candidate, actual signed merge, and installed release
qualification are separate obligations. No local native build or new-source
success is claimed during this preparation.

Unverified plain TS/JS/declaration/JSX/TSX write targets remain wholly refused;
read-only navigation and SFC-local imported aliases are preserved. Sound bare
exporter writable provenance remains unfinished under its separate owner. This
is not an installed-distribution catalog or universal product-parity claim.
Unix hardlink laws and relay controls do not qualify Windows hardlink handling.
Malformed legacy responses still use their existing unavailable-route policy;
the new recognized-WorkspaceEdit target laws do not qualify malformed replies.
