# One L2 query model for products

Decision for [#6871](https://github.com/ubugeeei-prod/vize/issues/6871)
(gate `levels.query`). It builds on the
[original File position queries](./2026-10-03-file-position-queries.md), the
[native script inventory](./2026-11-09-6844-native-script-inventory.md) (#6844)
and the LSP state decisions on
[#6872](https://github.com/ubugeeei-prod/vize/issues/6872). Where this record
and the 2026-10-03 record disagree about where a query lives, this record wins;
the 2026-10-03 query semantics (completion, half-open UTF-8 sites, no name
fallback, refusal on overlap) stay as they are.

## Problem

The charter promises one typed query API that every product reads
(`semantic-engine.md`, "One typed query API"; charter rule 3). What exists is
smaller and scattered:

- Five inherent `FileArtifact` methods in `vize_l2::file::query`
  (`reference_at_offset`, `binding_at_offset`, `scope_at_offset`,
  `template_symbol_at_offset`, `for_each_template_reference_to`), 674 lines with
  the template sites. Product callers: five sites in Maestro navigation. Canon
  reads `vize_l1_to_l2::native_file::NativeSfc`, a second query surface with its
  own reference type.
- The Vue script facts of #6844 (`SetupFacts`, `OrdinaryFacts`, `OptionsFacts`
  and the `ComponentContract`) are owned values that each caller threads by
  hand. Nothing ties them to the File they were observed over.
- Template usages (Croquis family 11: `ComponentUsage`, `PassedProp`,
  `template_expressions`, `ScopeKind`) have no native query at all. Croquis is
  the de facto semantic API: 322 `Analyzer`, 581 `Croquis`, 246 `ScopeKind`,
  154 `ComponentUsage` and 217 `Croquis.macros` product sites
  (`node tools/support/compat/davinci/croquis-consumers.ts --summary`, 2026-11-19).

`vize_l2` has no `Demand` type, and products import L2 internals
(`file::records`, `resolution`) directly, so an L2 change still breaks every
product.

## Decision

1. **One entry type.** Products read semantics through
   `vize_l2::query::Model<'f, 'a>`. A model borrows one completed
   `FileArtifact<'a>` (which already owns the canonical `Artifact` and its
   `ArtifactParts` side tables) and, optionally, the Vue fact families that
   were observed in the same Program walk. It is `Copy`, holds only shared
   references, and constructing it does no work:

   ```rust
   let model = Model::new(&file)          // script + template resolution
       .with_setup(&setup_facts)          // `<script setup>` facts, if observed
       .with_options(&options_facts);     // Options API facts, if observed
   ```

   The query code moves from `vize_l2::file::query` into `vize_l2::query`. The
   `FileArtifact::*_at_offset` methods stop being public, so there is one API,
   not a façade beside the old one. The handle types (`BindingRef`,
   `ReferenceRef`, `ScopeRef`, `TemplateSiteRef`, `TemplateSymbolRef`,
   `HandlerLocalRef`) and the error types are re-exported from
   `vize_l2::query`; a product needs no other `vize_l2` path to ask a semantic
   question.

2. **Method families.** Each family is one module under `vize_l2/src/query/`:

   | Family          | Questions                                                                                                                   | Built from                                                                | Slice |
   | --------------- | --------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------- | ----- |
   | Position        | What use, binding, scope or template site covers a byte                                                                     | `file::query` today, then the Q5 index                                    | Q2    |
   | Resolution      | A binding's declaration; every use of a binding in script and template                                                      | `Reference` rows, `FileResolution` occurrences, handler and `v-for` sites | Q2    |
   | Scope chain     | Parent, ancestors and lookup from a scope                                                                                   | `Scope` rows and their recorded parents                                   | Q2    |
   | Binding kind    | The Vue binding kind of a binding (setup ref/const/let/props alias, options member, ordinary)                               | `SetupFacts::bindings`, `OrdinaryFacts`, `OptionsFacts`                   | Q3    |
   | Vue contract    | Macro calls, props, emits, models, slots, expose, options members                                                           | `SetupFacts::{macro_calls, contract}`, `OptionsFacts`                     | Q3    |
   | Template usages | Component usages with resolved binding, passed and spread props, listeners, slots; template expressions with kind and scope | L2 ops of the canonical region and the template sites, no new walk        | Q4    |

   The binding-kind and contract families need no new producer: #6844 S2, S3,
   S6 and S7 already observe them. Q3 only attaches them to the model, keyed by
   the File's own `BindingId`s instead of names.

3. **Borrowed, allocation-free answers.** Every answer is a `Copy` handle that
   borrows the model's File, or an iterator/visitor over existing rows. No
   query allocates, sorts or clones. Visitors keep the existing contract: a
   late refusal invalidates everything already visited, and the caller
   discards it before publishing a response. Handles keep the same-owner
   checks of 2026-10-03: numeric IDs from another File are refused, never
   reinterpreted.

4. **Typed refusals.** The existing `PositionQueryError` and
   `TemplateQueryError` stay. Q3 adds one variant for a fact family the model
   was not given (`NotObserved(Family)`), and family-specific refusals for rows
   the producer left unclassified (`SetupFacts::unclassified`). No query falls
   back to a name lookup or to Croquis.

5. **Demand is what the caller observed.** A caller states the fact groups it
   needs by running those observers in the one Program walk and attaching
   their results to the model. Nothing else is computed. A query on a family
   that was not attached returns `NotObserved`, so a missing declaration is a
   typed refusal in every build, not a silent empty answer. The debug-build
   undeclared-access detector and the consumption-matrix staleness check of
   `semantic-engine.md` point 4 are out of scope here; whether
   `levels.query` requires them is a maintainer decision (plan question 4).

6. **The position index belongs to the snapshot (Q5).** Today's position
   queries scan the rows of one File, as the 2026-10-03 record states. For the
   LSP, Q5 adds a span-sorted position index, built once per snapshot on the
   first position request and dropped with the snapshot (the #6872 decision:
   no cross-edit node references, binary search per request). The index is
   owned by the caller and attached with `Model::with_index`; method
   signatures do not change. One-shot CLI and compiler callers never build it
   and pay nothing.

7. **L1-admission wrappers stay in L1→L2 until L2 owns the rows.**
   `NativeSfc` checks every template embed against its L1 syntax before it
   answers, which needs L1 types that `vize_l2` cannot name. Q2 leaves its
   checks in `vize_l1_to_l2`, but its position queries call the model instead
   of the removed `FileArtifact` methods. Q4/Q5 move its template-reference
   enumeration into the model once the File can enumerate its admitted
   expression resolutions itself.

8. **Template usages come from L2, not from a Croquis adapter.** Q4 follows
   the #6844 "no adapter" rule. Component usages, listeners, slot usages and
   template expressions are read from the canonical region's ops and template
   sites the File already holds. Each Q4 PR carries a dev-test that compares
   the query with Croquis on the repository corpus with exact equality;
   Croquis is a dev-dependency of that test only. Where Croquis disagrees
   with Vue, the row is classified as a Croquis defect, as in #6844 S7.

## Scope and order

| Slice | Change                                                                                                | Behavior risk | Proof                                                                                       |
| ----- | ----------------------------------------------------------------------------------------------------- | ------------- | ------------------------------------------------------------------------------------------- |
| Q1    | This record                                                                                           | none          | docs only                                                                                   |
| Q2    | `vize_l2::query::Model`; move `file::query`; move every caller (Maestro, `NativeSfc`, tests)          | none          | identical query tests; Maestro navigation fixtures; instruction rows and binary size ≤ base |
| Q3    | Binding-kind and Vue-contract families                                                                | additive      | equality with the existing `SetupFacts`/`OptionsFacts` readers                              |
| Q4    | Template usages, in three PRs: component usages; listeners and slots; expressions with kind and scope | additive      | exact-equality dev-test against Croquis on the corpus, defects classified                   |
| Q5    | Snapshot position index                                                                               | none          | equality with the scanning queries; LSP keystroke p95 and RSS ceilings                      |
| Q6    | Mechanical import check for products                                                                  | n/a           | changes the gate definition; needs maintainer approval and its own record                   |

A model that runs beside a Croquis analysis for the same consumer would raise
CPU and RSS. A product therefore switches one feature family to the model and
deletes its Croquis read in the same PR (LN3, TC5, LSP3). The gate closes when
those drains finish; this record makes the API complete, not the gate.

## Tradeoffs

- **Inherent methods versus a model type.** Keeping methods on `FileArtifact`
  would avoid touching callers, but the Vue facts are separate owned values,
  and a product would have to import `file`, `framework::vue` and
  `resolution` to ask one question. One borrowed entry type keeps the product
  imports to one path and lets L2 internals move.
- **Optional families versus one eager bundle.** Bundling every fact family
  into the File would make every compile pay for facts only the LSP reads.
  Optional attachment keeps the compiler's walk as it is and makes a missing
  family a typed refusal.
- **Scans versus an index.** Scans cost nothing to build and are what the CLI
  needs. The index is worth its memory only in a resident process, so it is
  owned by the snapshot, not by the File.

## Review

The LSP (#6850, #6872) and Canon (#6849) owners review the method families
and the `NativeSfc` plan before Q4 starts. Q2 and Q3 change no product
behavior and proceed under this record.

## Checking position lookups against original rows

The position index sorts half-open byte intervals by start and stores the greatest end in each subtree. That maximum lets it discard a whole subtree when the cursor is at or beyond its last end. The same augmentation appears in the interval-query example in PAM. Source coordinates have snapshot scope, as in rust-analyzer's distinction between immutable syntax and an absolute position on a syntax node. [Sun, Ferizovic and Blelloch, section 5.1](https://www.cs.cmu.edu/~yihans/papers/pam.pdf) · [rust-analyzer syntax](https://github.com/rust-lang/rust-analyzer/blob/master/docs/book/src/contributing/syntax.md)

The Lean model proves equivalence to a scan of the start-sorted rows for any finite tree shape. Removing empty or inverted ranges and permuting tied starts preserves every selected source row, including duplicates. Kani checks the production sorter, subtree maxima, visitor and unique selection for zero through three unordered rows with arbitrary 32-bit endpoints, cursor and selection mask. A second harness builds the real index for all eight patterns of retained and discarded rows, including duplicate spans, inverted ranges and nonconsecutive original row numbers. Both use an independent half-open scan. The native test also compares the complete constructor and queries on 16,464 combinations. [Interval theorems](../../../tests/formal/position-index/Intervals.lean) · [Rust oracle](../../../davinci/vize_l2/src/query/position/index/tests/checked_points.rs)
