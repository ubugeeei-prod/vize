# Check benchmark report TypeScript graph

The repository-owned executable TypeScript migration applies to the report half of
the check benchmark gate. This bounded slice supports [#6828](https://github.com/ubugeeei-prod/vize/issues/6828)
and [#6830](https://github.com/ubugeeei-prod/vize/issues/6830); both broad roadmap gates remain open.
The [migration foundation](./2026-10-08-owned-typescript-migration.md) supplies the
pinned native TypeScript project checker.

## Source and ownership

The provider is `tools/benchmarks/scripts/check-gate-report.ts`, with its original
budget tests moved to `check-gate-report.test.ts`. The first commit moves both files
with 100% Git similarity and no changed bytes. The successor adds erasable types,
the exact live caller imports, current workflow command and trigger assertions.

The measured producer, benchmark environment, compiler selection, corpus generator,
planted fixtures, timing parameters and performance budgets remain unchanged.
`check-gate.mjs` and `compare-tools-report.mjs` receive only the report import/path
updates. Their own migration and every other residual handwritten `.mjs` graph
remain unfinished.

## Contracts

- The existing cold loop initializes every variant before warmup. Its typed helper
  performs those same calls and assignments, then narrows the initialized state;
  it introduces no measurement phase or extra measured invocation.
- Every cold, warmup and measured output retains the expected diagnostic count
  guard. At least one warmup pass remains required. Rotation order, every cold
  value, measured sample, median, notes and row field remain unchanged.
- Budget results retain invalid-head, absent-baseline, invalid-baseline and passed
  or failed states. The rounded change and inclusive threshold remain unchanged.
- The complete Markdown retains both engine classes, skipped rows, binary hashes,
  source entry, backend readiness and the cross-engine attribution sentence.
- Stored artifacts, public package Node contracts and engine classification strings
  are not renamed or regenerated by this source migration.

`tsconfig.benchmark-reports.json` extends the existing strict Node configuration
and selects only the actual provider and test. It enables no JavaScript bypass,
suppression or broader repository project. The existing `check:repo` sequence runs
the foundation's warning gate and project check before this explicit project check.

## Qualification

Reproduce the bounded checks with the repository's pinned Node runtime:

```sh
vp exec node tools/support/typescript/check-project.ts tsconfig.benchmark-reports.json
vp exec node --test tests/tooling/check-bench-trigger.test.ts tests/tooling/tool-benchmark-trigger.test.ts
```

The four original budget tests and three additional complete-output/order/count
controls pass, alongside the two existing workflow trigger checks. An independent
local comparison with the literal `0bb7d231e70c318240337f35c74957488adde735` provider
retains 507 whole budget outcomes, 16 complete measurement/error observations and
four byte-exact Markdown outputs. The original engine map is identical. This is
deterministic reporter acceptance, not compiler throughput or accuracy evidence.

The existing check-bench trigger test imports the actual report test module so
those same seven laws execute in the existing PR tooling worker. The scheduled
benchmark also retains its direct test invocation; repeated execution of those
laws is not independent coverage or a new workflow stage.

All seven existing caller test modules execute locally: 23 tests pass and the two
tests requiring a built source CLI remain explicitly skipped. The first local CLI
refusal test exposed an uninstalled benchmark Vue package; installing no new
version and resolving the existing pinned `3.6.0-beta.10` package restores its real
planted-diagnostic refusal. Original source CLI qualification remains required on
Actions; no skipped or synthetic binary test grants native performance credit.

Local bootstrap is the pinned Node `24.14.0` and native TypeScript `7.0.2`. Existing
benchmark workflows already establish that Node runtime before invoking the report
tests; their measurement schedule, installation order, commands and parameters are
retained. Exact source Actions, protected Stack delivery and fresh-main verification
remain pending. Queue admission belongs to the root owner.
