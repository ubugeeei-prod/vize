# Cache the Vite+ Node.js bootstrap

Issue: [#6830](https://github.com/ubugeeei-prod/vize/issues/6830).
This follows the measured setup cost in
[the source-planner CI record](./2026-10-13-source-planner-ci-cost.md).
No check, corpus, ceiling, or required status is removed.

## Cause

On [PR Check 38341424403](https://github.com/ubugeeei-prod/vize/actions/runs/38341424403),
Rust shard 3 job 115119603586 logged `Preparing Node.js and pnpm...` at
03:49:51 and `Installing dependencies...` at 04:00:24. That 633s gap is
inside the global Vite+ 1.1.0 installer, before project `vp install`.
The same gap was 715s in `node-engine-compat` (22), 224s in
`check-vize-apps`, 137s in the source CLI producer, and 12s or 2s in
`check-js` and the JS package job. The project dependency cache then
hit the same `vite-plus-Linux-x64-pnpm-…` key and downloaded zero
packages.

Vite+ 1.1.0 shows that line from one spinner around
`prepare_install_runtime`: resolve the latest Node.js LTS, download it,
then download pinned pnpm. CI is not a TTY, so the spinner prints once.
`download_timeout` in that release is 10 minutes per attempt, and a
present binary at `<DATA>/js_runtime/node/<version>` skips the download.
`setup-vp` forces `VP_HOME=~/.vite-plus`, so the data directory is the
monolithic home. The gap is a Node tarball attempt that can sit until
that timeout. It is not a second project install and not a pnpm-store
cache miss.

## Decision

Restore `~/.vite-plus/js_runtime` and `~/.vite-plus/package_manager`
with `actions/cache` immediately before every pull-request `setup-vp`
on the source, Rust, and JS lanes. The key is
`vp-bootstrap-v1-${runner.os}-${runner.arch}-node-${latest-lts}`, where
the version is the highest `x.y.z` index entry whose `lts` field is a
codename. That is the version the installer asks `download_runtime` for,
so an exact hit is the directory the installer will reuse.

Only `push`, `schedule`, and `workflow_dispatch` on the default branch
can save, and only the job that passes `save: true` does. Pull requests
and the merge queue restore that one entry and do not write it. A
pull-request save would be invisible to other pull requests, and a
per-ref copy would compete with the Rust caches. The differential seed
on the same main push restores and does not reserve the key. The
trusted writer is a short job on the existing main-branch Rust seed
workflow, with `actions: write` on that job alone. `check.yml` still
calls `setup-vp` directly; #9118 was editing that file when this slice
was cut, so `node-engine-compat` and `check-vize-apps` are unchanged
here.

A failed index lookup skips the cache step and leaves the existing
installer path in place. This run cannot show a warm Actions restore:
the key does not exist until a default-branch seed saves it.
