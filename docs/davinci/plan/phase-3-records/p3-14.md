# P3-14 — `folio-reduce` (`vize reduce`)

**Landed 2026-09-22.** `vize reduce` shrinks a failing SFC or a crash
reproducer while it keeps failing the same way. It follows the llvm-reduce
model: a dumb deterministic driver, an IR-aware deletion vocabulary, and a
sovereign interestingness predicate.

## Shape

- **Vocabulary: S1 subtrees.** `crates/vize/src/commands/reduce/vocabulary.rs`
  lists every node and attribute of the artifact's lossless S1 surface tree
  as a byte range, in pre-order. That covers the whole SFC, so `<script>` and
  `<style>` blocks are candidates too. Each range starts at the first token's
  `leading` slice, so a deleted element takes its indentation with it.
  S1 renders its input byte for byte (TS-19) and parses any input, so a
  deletion always leaves a re-parseable, re-printable artifact. Unit laws
  check this: exact ranges on a small input, and on the seeded fixture every
  pair of candidates is either disjoint or nested.
- **Driver: ddmin over the candidates.** `reduce/driver.rs` tries to delete
  a chunk and keeps the deletion when the predicate holds. After each kept
  deletion it re-enumerates the candidates, and when a pass keeps nothing it
  halves the chunk size. A pass at size 1 that keeps nothing is a fixpoint,
  so the result is **1-minimal** with respect to the vocabulary. The unit
  test re-derives that claim independently: no single remaining candidate
  of the result can be deleted without losing the oracle. The driver also
  enforces a run budget (`--max-runs`) and is deterministic, so reductions
  can be pinned exactly.
- **Oracles: composable by listing.** `reduce/oracle.rs` builds a conjunction
  of checks:
  - `Reproduces`: for a `*.repro.folio` input, the repro with the candidate
    as its artifact replays to the recorded failure, byte-equal.
  - `--crash`: the candidate's compile panics.
  - `--remark "<stage.pass> <kind> <name>"`
  - `--folio-contains` (text in the S2 folio)
  - `--diagnostic` (text in an S1→S2 diagnostic message)
  - `--walks-over N` (a budget breach of the S2 transform pipeline)
  - `--script CMD`: the sovereign interestingness script,
    `sh -c "CMD <file>"`, which exits 0 when interesting.

  The S2-based checks share one run per candidate: lowering plus the
  transform pipeline under `Pair(BudgetObserver, RemarkCollector)`. That is
  the same channel TS-32 and the Spolvero feed read (P3-13).

- **Repro packages reduce directly.** A `repro.folio` is reduced on its
  `source` artifact, and the output is again a repro folio that `vize repro`
  accepts. This matches how the ICE machinery (charter #30,
  `commands/davinci_ice.rs`, `commands/repro.rs`) is structured, which is
  why `vize reduce` sits beside `vize repro`.

## The seeded crash (acceptance)

A plain TS-23 injected panic fires whatever the artifact says, so reducing
against it would be vacuous. `--davinci-inject-panic <stem>:<pass>:<tag>`
(and the matching `inject-when` repro config) makes the injected crash
**content-dependent**: the pass panics only while the source's S1 tree still
contains an element named `<tag>`. That is the shape of a real
construct-triggered compiler bug.

`crates/vize/tests/davinci_reduce_cli.rs` pins, exactly:

- The committed `seeded-crash.repro.folio` is byte-identical to what a
  seeded `vize build` writes for the 3733-byte fixture
  `seeded-crash.vue`. That fixture is an in-repo ecosystem SFC with
  `<seed-crash>` nested five elements deep inside a `v-for`. The same build
  over the same file with the element renamed compiles normally.
- `vize reduce` on the repro produces
  `reduce: 3733 -> 117 bytes (3.1% of the input), 62 oracle run(s), 1-minimal`.
  The output equals the committed `seeded-crash.reduced.repro.folio`, whose
  artifact is
  `<template><section><Swiper><SwiperSlide><article><seed-crash /></article></SwiperSlide></Swiper></section></template>`.
  That is **3.1% ≤ 20%**. `vize repro` on the output reports that it
  reproduced the recorded `template.transform` injected panic.
- The seed is load-bearing: the renamed repro does not reproduce, and
  `vize reduce` refuses it (exit 1).
- Each `.vue` oracle reduces its input to an exact witness. `--remark`,
  `--folio-contains`, `--script`, `--diagnostic`, and `--diagnostic` combined
  with `--walks-over` produce witnesses of 63–141 bytes. Every refusal message
  and exit code is pinned.

## Remaining

Nothing in P3-14's acceptance remains open. Reducing S2/S3 folio artifacts
directly (a folio-stage deletion vocabulary) waits until the compile path
records non-source last-good stages in its repros. Today every repro carries
`artifact-stage=source`, and `vize reduce` refuses the others by name.
