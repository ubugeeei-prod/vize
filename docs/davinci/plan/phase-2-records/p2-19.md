# P2-19 — DevTool protocol spike

**The transport question closed: document over JSON-RPC. The schema-versioned
feed document (P2-18) stays the unit on every surface; the C-7 local server
will speak content-mapper-style JSON-RPC whose `initialize` negotiates the
feed `schema_version` before any payload is serialized; served files remain
the at-rest form; the wasm playground keeps the P2-18 embedding; JSON-lines
streaming is rejected. Decided 2026-08-21; the spike was deleted — this
record carries the measurements and the reproduction recipe.**

## Method — what was prototyped, against what

One spike test file (`crates/vize_davinci/tests/p2_19_transport_spike.rs`,
now deleted — see Disposition) drove all three candidates against two P2-18
feeds:

- **The real `davinci-opt` feed**: the TS-52 command line
  (`--pipeline "s2(alpha,beta)" --stage budget-observer --folio-dir <dir>`)
  over the canonical `[budget-observer]` artifact on stdin — 2 pages, a
  312-byte `spolvero.json`.
- **A stage-ladder feed at honest scale**: 24 pages × 64 folio-like lines
  (~5.2 KiB per page), built as a `SpolveroFeed` and serialized by the one
  producer, `to_json` — a **126,637-byte** document, the scale of one
  component viewed across every pass.

The candidate framings, small enough to restate completely:

- **(a) JSON lines** — line 1 a header object `{"schema_version", "command"}`
  (43 B), then one compact-JSON page object per line. Consumer checks the
  header, then reassembles `{schema_version, command, pages: [...]}` from the
  page lines; the oracle is exact equality with the parsed `to_json`
  document.
- **(b) served files** — the production P2-18 surface unmodified:
  `davinci-opt --folio-dir` writing pages + `spolvero.json`
  (`src/bin/davinci-opt/export.rs`), timed end to end through the spawned
  binary, plus write/read+parse of the ladder document.
- **(c) JSON-RPC** — `vize content-mapper`'s framing verbatim
  (`Content-Length: N\r\n\r\n` + body, `crates/vize/src/commands/content_mapper.rs`
  precedent): `initialize` takes `{protocolVersion, spolveroFeedSchemaVersion}`
  and errors `-32602` on mismatch **before any payload exists**; `feed`
  returns the whole document; `page {index}` returns one page. Driven
  in-process over in-memory pipes; oracles are exact equality of the `feed`
  result with the document and of the refusal message.

Byte counts are deterministic and exact. Timings are a debug build on Apple
Silicon over three runs — quoted as ranges, and only the _shape_ (orders of
magnitude, what grows with what) informed the decision.

## Consumer fit (the three devtool.md surfaces)

| consumer                                   | (a) JSON lines                                        | (b) served files                 | (c) JSON-RPC                                              |
| ------------------------------------------ | ----------------------------------------------------- | -------------------------------- | --------------------------------------------------------- |
| browser playground (`vize_vitrine` wasm)   | unreachable (no sockets), and reassembly needed first | unreachable (no directory reads) | unreachable (no child processes)                          |
| `--format agent` (`AiContextBudget` shape) | must drain the whole stream before budgeting          | fits — one document              | fits best — budgeted pull-by-page (83 B per page request) |
| local server (C-7)                         | one-way; no mid-stream re-negotiation; replay joins   | polling only                     | request/response + handshake; framing already in the tree |

The wasm row decides more than it appears to: **no transport reaches the
playground at all** — wasm can open no socket, read no directory, spawn no
process — so the P2-18 embedding (the feed _value_ inside the inspector
payload / `analyzeSfc` result) is the wasm delivery under every candidate,
and the embedding requires the feed to keep a single-document form. The
agent row is shaped by `vize_doctor::ai_context`
(`crates/vize_doctor/src/ai_context/contract.rs`): `AiContextBudget` applies
deterministic byte/count limits over a complete in-memory value with
recorded omissions, so a budgeting consumer holds the whole feed regardless
of how it arrived.

## The decision, and why

**Document over JSON-RPC.** The feed document stays the unit everywhere; the
only open surface, C-7's local server, speaks content-mapper-style JSON-RPC:
`Content-Length` frames, `initialize` negotiating the feed `schema_version`
before any payload, then whole-feed or per-page pulls whose results are the
unchanged P2-18 document and pages. Served files remain the at-rest/CLI form
(`davinci-opt --folio-dir` + `spolvero.json` — already production, TS-52);
the playground keeps the P2-18 embedding.

- **Transport does not change the payload.** Full-feed delivery costs the
  same order in all three (126.6 KB vs 126.6 KB vs 132.1 KB) — so the
  question is not "which serialization" but "how does the server hand the
  same bytes over", and the document form every consumer needs is preserved
  only if the document stays the unit.
- **The negotiation requirement is the discriminator.** devtool.md's data
  layer requires Spolvero to _negotiate_ on `schema_version` and refuse
  loudly. Files and lines can only refuse after the fact — the producer has
  serialized everything before any consumer looks (all 126,637 B written
  against a 20 B detection read). Only the RPC handshake refuses before any
  payload exists (130 B → 139 B, zero payload serialized) — and it is the
  only shape where negotiation can _succeed_ across versions, exactly as
  content-mapper's `initialize` does for `protocolVersion`.
- **The incremental grain is the page — which files lack.** A one-page
  change costs ~5.2 KB in (a) and (c) but 126,637 B written _and_ re-read in
  (b), amplification that grows with the feed. Between (a) and (c), the RPC
  page pull matches the stream's grain (+57 B envelope) while keeping
  random access, late joins without replay, and the handshake.
- **JSON-lines buys nothing a named consumer can use.** Both push-style
  consumers reassemble the whole document anyway (wasm embedding, agent
  budgeting); a stream cannot re-negotiate mid-flight; late joiners replay.
  Rejected.
- **Startup does not discriminate.** One-shot files and a resident server
  both answer in milliseconds; first-spawn cost is a property of process
  creation, not of any candidate.

Non-goals stand: this record decides the _shape_; building the server is
C-7, and auth/remote access and the JS plugin API remain out of scope.

## Disposition — spike deleted

The spike (one test file, 372 lines) was **deleted, not kept**:

- Candidate (b) already lives in the tree as production code with TS-52
  tests — nothing to keep there.
- The RPC winner is C-7's to build at production quality (an explicit
  non-goal here); a kept toy server would have no consumer, which is
  precisely the "spike code left lying around" failure mode this task's
  acceptance names.
- The refusal law the decision leans on is already pinned in the tree: the
  TS-52 suite asserts the exact `schema_version` const-violation message.
  The handshake precedent lives in `content_mapper.rs` (`initialize`
  rejects a wrong `protocolVersion`; its tests pin the successful
  handshake) — C-7 owes the rejection path a pin when it builds the real
  server.

Reproduction: the framing shapes above are complete; the ladder fixture is
24 pages of 64 lines, each line
`  %{page:02}.{line:02} = disegno.op attr="value-{line:04}" span=[{line}, {page}] ; ladder filler text row`,
pages alternating `s1`/`s2` with `pass-{page:02}`, path `src/App.vue`,
serialized by `SpolveroFeed::to_json`; the real-feed run is TS-52's
`run_folio_dir` command line quoted in Method; measure with a `#[test]`
printing byte counts and `Instant` timings under `--nocapture`.
