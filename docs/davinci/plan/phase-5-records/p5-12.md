# P5-12 — Multi-client LSP conformance (TS-45)

**Status:** landed. TS-45 is green for all four clients on `main`
([Editor conformance run 35643771593](https://github.com/ubugeeei-prod/vize/actions/runs/35643771593),
commit `10b50d058`), after #6317 (suite), #6324 (harness fixes) and #6321
(server fix). The Zed row is a protocol replay, labeled as such everywhere
the result is shown.

## What TS-45 is

One scenario (`tests/editor-conformance/scenario.json`) with one set of exact
expectations (`tests/editor-conformance/expected/*.json`), played through each
editor against the real `vize lsp`:

| #     | Step                          | What the client does                                        | Judged exactly                                    |
| ----- | ----------------------------- | ----------------------------------------------------------- | ------------------------------------------------- |
| 1     | initialize                    | starts the server from its packaged integration             | `initializationOptions` sent, full `capabilities` |
| 2     | open                          | opens `src/Scenario.vue` from the shared `real-vue` fixture | `languageId` and text of `didOpen`                |
| 3     | diagnostics on open           | —                                                           | settled publish (lint + TS 2322), version         |
| 4–6   | hover, completion, definition | its own hover / completion / go-to-definition               | complete response                                 |
| 7     | code actions                  | code actions on the lint span                               | complete response                                 |
| 8     | apply quick fix               | applies the preferred fix through its own edit machinery    | document text the server received                 |
| 9     | diagnostics after quick fix   | —                                                           | settled publish, version                          |
| 10–11 | formatting, apply             | formats (tab size 2, spaces) and applies the edits          | response, then resulting text                     |
| 12–13 | typed edit, diagnostics       | replaces `"3"` with `3`                                     | resulting text, then an empty settled publish     |
| 14–15 | rename, apply                 | renames `total` → `quantity`                                | workspace edit, then resulting text               |
| 16    | shutdown                      | stops the server                                            | answered `shutdown`, `exit`, process exit code 0  |

The editors' own requests go through `tests/editor-conformance/lsp-tap.mjs`,
a byte-transparent proxy placed first on `PATH` as `vize`, so every client
launches the server exactly as its package does. The tap writes a JSONL
transcript; `conformance.ts` judges only that transcript, with the same code
for every client. Positions are UTF-16 (the only encoding all four offer and
the one the server negotiates). Diagnostic order inside one publish is
canonicalized; nothing else is.

### The negative control (acceptance: "a deliberately wrong expectation fails")

`negative-control.ts` re-judges each client's real transcript sixteen times,
each time with one step's expectation corrupted; every corrupted step must
fail, or the client is reported non-conformant. The result table prints
`rejected 16/16` per client. `tests/tooling/editor-conformance.test.ts` proves
the same on a synthesized ideal transcript, plus: a wrong response, a server
error, a missing request, a stale diagnostic version, a second server session
and a crashed shutdown each fail; batched incremental edits are judged by the
states the server applied.

The text expectations are an independent oracle for the response
expectations: the tooling test applies the expected code action, formatting
edits, typed edit and rename edit to the authored text and must arrive at the
scenario's text steps.

## Findings

- **Server bug, fixed in vize (#6321):** Neovim's default exit
  (`exit_timeout = false`) sends `shutdown` and closes the server's pipes
  without waiting; the server's next log line hit the closed stderr and
  tracing-subscriber's internal-error `eprintln!` panicked (exit 101). The
  subscriber no longer reports internal errors; `lsp_survives_a_closed_stderr_pipe`
  in `crates/vize/tests/lsp_cli.rs` is the regression test. The Neovim
  driver still stops the client the way `:lsp stop` does, so the shutdown
  step judges the full `shutdown`/`exit` handshake.
- **Harness defects, fixed in the suite (#6324):** Helix drops its server
  child with `kill_on_drop` right after `exit`, and — leading the pty session —
  its own exit hung up the terminal; the tap now records the server's exit
  from a `/bin/sh` wrapper that outlives it, and a shell leads the pty session
  as in a real terminal. VS Code restarted the language client on every
  settings change, so the document reached two server sessions; the workspace
  settings are now in place before launch.
- **No per-client expectation exists:** all four clients receive byte-identical
  capabilities and responses; the only client-side inputs the scenario pins
  (tab size 2 with spaces, the formatting opt-in) are set through each
  client's own user-facing configuration.
