**Reason: the shipped release binaries grow.** The size rule judges the release profile (fat LTO, one codegen unit), and that size must not grow. This change grows both shipped binaries:

| `vize_vitrine` N-API library (`napi,legacy`) | 80,235,968 | 80,350,704 | **+114,736 (+0.14%)** |

The CI-optimized Linux CLI in this head's PR performance observation ([run 45319290942](https://github.com/ubugeeei-prod/vize/actions/runs/45319290942)) grows the same way: 79,582,936 → 79,758,680 bytes (+175,744).

**Where the bytes go.** I diffed the text symbols of the two release N-API libraries. SSR and Vapor now lower through the `NoProvenance` sink. With more callers, LLVM inlines far more into that copy of the Vue lowering. The `Vec<ProvenanceRecord>` copy is still linked for stage capture and the other recording callers, so both copies stay in the binary:

The 11-19 rules reject metric trade-offs, so the allocation and Criterion gains (Vapor −6 to −14%) cannot offset the size growth. Two ways to land the gain without the growth:

- Keep a single monomorphization of the Vue lowering. For example, make the record sink a runtime choice on one instantiation, or move every remaining recording caller onto an observer, so that the `Vec` copy leaves the shipped binaries.
- Bound the inlining growth in the `NoProvenance` copy (`#[inline(never)]` on the per-child lowering helpers), then re-measure every release instruction row.

Either one needs a fresh release-profile measurement with A/A twins (`shipped-profile-measure.yml`) before it reopens.
