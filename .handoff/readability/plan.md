# Readability program plan

The maintainer's order (2026-11-24): "ソースコードの可読性をとにかくあげる (Rust のみならず，全てが対象)".

This plan turns `style-guide.md` into work and uses `inventory.md` as its baseline. It is part 3 of the 11-24 cleanup program: drain PRs, then workflows, then tools, then readability. It is written to run beside the workflow plan (`../workflows-plan/plan.md`) and the tools plan (`../tools-plan/plan.md`) without editing the same files at the same time.

## 1. Summary

- **The problems are concentrated, not everywhere.** Comment density is low (1.3% plain, 4.7% doc), and 98% of files are under 500 lines. The real debt is:
  1. 172 oversized files (110 product), plus 22 more in `tools/` that are exempt from the gate.
  2. 1,686 long functions without a single blank line.
  3. 2,667 issue-number comment lines and about 2,800 restating or narrating comment lines.
  4. Five unit-test layouts, 442 issue-numbered file names and a flat 1,832-file `tests/tooling`.
  5. Mixed import grouping (4,089 Rust and 3,450 TS files).
  6. Hardcoded limits, versions, repo paths and re-implemented helpers (1,548 local `repoRoot` definitions).
- **Three hidden traps make "comment-only is free" false in this repo** (§3.3):
  1. Every `#[track_caller]`/panic site embeds file, line and column in a `core::panic::Location` constant. Deleting a comment line changes the IR of every later panic site in that file.
  2. Doc comments on clap, napi and wasm-bindgen items are shipped text.
  3. Generated rule pages pin `#L<line>` anchors into patina sources.
- **About 480 sources are byte-custody pinned** by tests, 182 of them product Rust files (§4). They are skipped until the custody step releases them.
- The work is split into **12 lanes**, run in 5 phases, for about **30 PRs** in total (§6–§7). The tooling PR comes first, then the style decision, then a pilot sweep on idle crates.

### 3.3 The traps, and what each lane does about them

1. **Panic `Location` constants (affects N0 and N1).**
   - What: rustc materializes `core::panic::Location { file, line, col }` for every `#[track_caller]` call and every compiler-inserted panic. That covers `Vec::insert`/`remove`/`swap_remove`, `RefCell::borrow_mut`, integer `/` and `%` by a variable, `copy_from_slice` and so on. One example is `davinci/vize_l4/src/targets/dom/artifact/buf.rs:187` `self.preferred.insert(at, helper)`.
   - Why it matters: `ir-normalize.ts` names anonymous globals by a hash of their initializer. So a comment deleted above such a site makes the IR differ in a constant, though no instruction changes. Release size is unchanged, but the binary hash changes.
   - Fix: L0 adds `--normalize-locations`. It recognizes `Location` initializers (a pointer to a `*.rs` path string plus two `i32`s), replaces line and column with a placeholder, and **counts** the normalized sites. Token identity proves nothing else changed.
   - Splits: moving code into a new file adds one path string per new file that has panic sites. That is about 40 bytes of `.rodata`, which may or may not show in the file size (Q2). The report gives the exact count.
   - Workspace lints already deny most panics (`unwrap`, `expect`, indexing, `panic!`), so most moved code has zero sites.
2. **Names that become bytes (affects N1).**
   - What: `#[derive(Debug)]` (3,669 derives) and `type_name` embed type and field names as strings; serde derives (359 files) put field names on the wire.
   - Why it matters: renaming such an item changes `.rodata` and possibly output (debug dumps, JSON, snapshots).
   - Fix: the rename codemod classifies every renamed item. Debug-only → allowed, with the byte delta reported (Q7). Serde-visible, napi-visible or CLI-visible → not renamed in readability lanes.
3. **Doc comments that are product text (affects N0).**
   - clap `Parser`/`Args`/`Subcommand`/`ValueEnum` derives (28 files): `///` is `vize --help`.
   - `#[napi]` (47 files): `///` goes into `npm/native/index.d.ts`.
   - `#[wasm_bindgen]` (12 files).
   - Fix: the comment codemod skips doc comments attached to these items. Token identity reports doc-attribute changes separately, and any doc change on such an item fails the N0 check.
4. **Line anchors in generated docs (affects N0 in `vize_patina`).**
   - What: `docs/scripts/generate-patina-rules-page.ts` records the `META` line, and the rule pages carry `…rs#L34` (1,864 anchors, 5 locales).
   - Fix: every patina sweep regenerates the pages in the same PR, or Q9 removes the anchors first. The latter is better: it saves a 1,800-file docs diff on every patina edit.
5. **Pinned bytes**: §4.
6. **Formatting can grow over-limit files.**
   - What: grouping imports adds 1–2 blank lines per file, and blank lines between items add more.
   - Fix: the sweep codemod applies comment deletion first and checks `lines(head) ≤ lines(base)` for every file over 500. If a file would grow, it is left for the split lane (L5), which runs before formatting for that file.

## 4. Byte custody procedure

1. **Registry (L0).** `tools/config/byte-custody.json` lists every source whose current bytes a test pins: path, digest, owning test, record and reason. `tools/commands/ci/byte-custody.ts --check` (an extended `scripts/pins.py`) fails when:
   - a tracked source's digest appears in the tree but is missing from the registry, so new pins must register;
   - a registered file changed while its owning record did not.

   The seed is today's 480 enforced pins (`data/pins/pinned-classified.tsv`). The 404 record-only pins are listed as `stale-ok`: an edit leaves a historical record and is allowed.
2. **Skip by default.** Every sweep codemod reads the registry and leaves enforced files untouched. The pilot and early lanes therefore never touch them.
3. **Release (L2, needs maintainer answer Q5).** For each custody family, pick one of three exits:
   - **Delete.** The pin backs a one-off evidence chain for a closed issue. This matches tools-plan D5; the content-mapper transitions and `*-custody.test.ts` families are the bulk. Delete the record, the transition and the test together.
   - **Freeze.** The history matters. Copy the pinned bytes once into `tests/_fixtures/tooling/source-custody/<sha256>.txt`, repoint the record from the live path to the frozen copy, and the live file is free. The test proves the same chain against immutable bytes.
   - **Keep and re-pin.** Only when the pin guards live behaviour, which is rare. The edit adds a custody layer (JSON record + Rust layer + TS transition, as the fleet brief describes for `generator.rs`), and the line count must not grow.
4. **Order.** Release `generator.rs` and `crates/vize_atelier_sfc/src/compile.rs` first: they hold the two longest product functions (666 and 637 lines). Then `vize_canon` (68), `vize_maestro` (43), `vize_patina` (42) and `vize_glyph` (24 enforced, 52 record-only).

**Conflict rules:**
- **Do not touch** `.github/**`, `tools/config/pkl/**`, `tools/**` or `tests/tooling/**` before workflow J and tools Phase 2 have merged. Phase B lanes touch only `crates/<idle>/**`, `npm/{ui,compose,…}/**`, `playground`, `docs/{theme,scripts}`, `examples` and `editors`.
- **Before starting an area**, run `gh pr list --state open --json files` and skip any area an open PR touches. Re-check right before pushing. Because sweeps are generated, the remedy on conflict is to reset to `origin/main`, re-run `sweep.ts` and re-prove; never hand-rebase a 1,000-file diff.
- **The codename rename and the `L1Ir` renames go first in their areas.** Ask the maintainer when (Q10). Until then, no readability PR touches `davinci/**`.
- **Third-party fixes** pre-empt everything: a lane pauses pushes and dispatches while one is in flight (fleet rule).

## 8. CI budget

- About 30 PRs over the program; at most 4 lanes active at once, each with ≤ 2 PRs in flight and ≤ 2 dispatches.
- Class T and N0 PRs need **no** instruction-count dispatches if Q1 is accepted. Their proof is local or comes from one `03-ir-identity` dispatch plus the automatic PR performance observation. That is the main CI saving.
- N1 PRs need one IR-identity dispatch plus one release-size probe each.
- Class C PRs need the full set and run one at a time per area.
- Every Rust PR runs the full suite (about 6,150 tests) in the merge queue anyway, which is another reason to keep the PR count low.

## 9. Risks

| Risk | Mitigation |
| --- | --- |
| Panic-location constants make N0 and N1 IR differ | `--normalize-locations`, token identity, size equality, and the maintainer's acceptance (Q1, Q2) |

| Heuristic false positives delete a meaningful comment | Only issue numbers, banners and the precise restating rule are automatic; history and commented-code findings are reviewed by hand; every PR lists deleted comment counts per rule |
| Semantic comments deleted (`@__PURE__`, `@vite-ignore`, `sourceMappingURL`, Vue template comments) | Hard keep-list in `sweep.ts`, plus AST identity, which notices PURE annotations because oxc keeps them on the node |

| Rename breaks deep imports of published packages | Q8; `exports` map unchanged check |
| Moving `tests/tooling` breaks the tooling planner | Phase C only; planner byte-identity on recent diffs; full tooling suite |
| Nightly rustfmt drift | Pin the date in the Nix shell; only the formatter, never the compiler; Q3 |
| The program stalls half-done and leaves mixed styles | The ratchet is per area: an area is either swept (counts frozen at the new level) or untouched; the inventory is re-run after each phase |
| Kept workflows are already red (workflow plan risk 7) | Not this plan's problem, but do not count red jobs as evidence; use the dispatches named above |

## 10. Open questions for the maintainer

1. **Comment-only evidence.** May N0 PRs pass on token identity, IR identity with panic-location line/column normalized, and an identical release size, *without* instruction-count tables (as move/rename-only PRs do)? The line numbers inside `Location` constants are the only codegen difference a comment edit can cause.
2. **Path strings in splits.** When a split moves code that has panic sites into a new file, the release binary gains one file-path string (about 30–60 bytes).
