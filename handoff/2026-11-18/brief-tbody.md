## Mission: SFC templates keep authored table rows (compiler parity with Vue 3.5)
Vize's compiler inserts an implied `<tbody>` (and `<tr>`) for `<table><tr>…` in a `.vue` template. Vue 3.5's compiler emits `table > tr` as written, and only warns ("<tr> cannot be child of <table>, according to HTML specifications"). This changes the runtime DOM compared with Vue (`table > tr` selectors, `$el.children`, and hydration of SSR output that Vue itself emits as `<table><tr>`). It is not documented as an intentional difference. It is not in `tests/_fixtures/compat-documented-differences.json` or the docs. #12387 already moved component parsing toward "keep authored table structure, browser-compatible implicit rows in document mode" for cells under sections. The orchestrator decided to fix it: make SFC/component template output match Vue 3.5, with no implied `tbody`/`tr` and Vue's warning kept where Vize emits one. In-DOM/document mode keeps browser behaviour.

Where it happens (both paths must change together and stay byte-identical with each other):
- Legacy parser: `crates/vize_armature/src/parser/element/table.rs` (`handle_in_table_start_tag` → `ensure_table_section`/`ensure_table_row` → `push_implicit_element`). The parser has a `document` flag (`crates/vize_armature/src/parser.rs`, set in `constructor.rs`): component mode is `!self.document`. `test_parse_table_inserts_implicit_tbody` in `crates/vize_armature/src/parser/tests.rs` pins the current behaviour; split it into component (authored rows) and document (implicit tbody) expectations.
- Native lowering: `davinci/vize_l1_to_l2/src/lower/table.rs` synthesizes `lower.table.implicit-tbody`/`implicit-tr` owners during L1→L2 lowering. Find out which inputs reach it (component templates and/or in-DOM documents) and stop synthesizing for component templates only.
