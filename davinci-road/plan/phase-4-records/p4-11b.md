# P4-11b — Composed cross-component conformance

**In progress (not yet claimed).** The composed check, the CLI rule and the
runnable example landed in #6342. TS-36 witness verification and the FP-3
fix landed after that. Only the P4-3b keying under "Open" remains.

## Boundary

`html/cross-component-nesting` is the check no per-file tool can make: every
template is valid on its own, and the collision appears only where a parent
renders a child. `vize lint --cross-file` resolves each component usage
through the parent's imports, re-checks the child's whole template in the
parent's open-element chain with the P4-11a checker
(`crates/vize_patina/src/html_content_model/composed.rs`), and reports at the
usage site every verdict that differs from the child's standalone check.

## Decisions

| subject            | decision                                                                                                                                                                                                                    |
| ------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Resolution         | Imports only (`CrossFileAnalyzer::resolve_imported_component`); an alias follows its import, a same-basename file elsewhere is never picked.                                                                                |
| Roots              | Single roots, every `v-if`/`v-else` alternative and every fragment root; nested component roots are followed while the chain reaches the parent.                                                                            |
| Unknown is silent  | Unresolved tags, dynamic `:is`, `<slot>` pass-through, recursion (revisited file) and depth > 16 stop the chain.                                                                                                            |
| Branch feasibility | `v-if` conditions are not evaluated (same domain as P4-11a), with one exact exception (FP-3): a child `v-if="prop"` is pruned at a usage that leaves `prop` unpassed when the child's script proves the absent value falsy. |
| No duplicates      | A child verdict equal to its standalone verdict is left to the per-file `vue/permitted-contents`.                                                                                                                           |
| Witness            | The message names the child element, the component chain and the child position (`<div> (rendered by <InfoCard> at src/components/InfoCard.vue:6:3)`); the label marks the parent element it collides with.                 |

## Prop-sensitive pruning (FP-3)

A child subtree is left out of a composed check only when all of this is
proven:

- its `v-if` is a bare identifier, and no `v-for`, `v-slot` or `slot-scope`
  scope encloses it, including the element's own;
- the usage passes no prop of that name. Static attributes, `:x`,
  `v-bind:x`, `v-model[:x]` and `@x` (as `onX`) are compared camelized, and
  a spread or a dynamic argument means any prop may be passed;
- the child's `<script setup>` declares the prop in a form the oracle reads
  (`crates/vize/src/commands/lint/cross_file/absent_props.rs`). Those forms
  are a type literal, a runtime object or array, `withDefaults`, or a
  destructure. The absent value must be falsy: no default, or a `null`,
  `undefined`, `false`, `0` or empty-string literal. No other top-level
  binding of either script block may carry the name.

In every other case the branch stays in, so pruning only removes what the
usage provably does not render.

## Witness (TS-36)

Each composed finding is a proven diagnostic. Its chain is the deciding
ancestor element (`HtmlElements`, stratum 0), then the violation at the
usage site (`HtmlComposedNesting`, stratum 1). Both are fact groups over the
composition's evidence (`html_content_model/witness.rs`, ids 10 and 11). The
CLI reports a finding only after the P4-6b verifier accepts its chain
against those facts.

## Mechanical witnesses

- `cargo test -p vize_patina --lib html_content_model` (composition fixtures:
  collisions, conforming compositions, alternatives and fragment roots, nested
  chains, unknown stops)
- `cargo test -p vize --test lint_cross_component_cli` (the
  `examples/html-conformance` JSON report, exact; aliased and same-basename
  resolution; FP-3 pruning against `null`, truthy, destructured and runtime
  defaults)
- `witness_tests` (every composed witness verifies; a moved span and a missing
  key fail with the exact `WitnessError`) and `prune_tests` (the guard is
  pruned only when it is unpassed and the oracle proves it falsy; passed,
  bound, kebab-case, spread, dynamic, shadowed and non-bare guards stay in)

## Corpus triage (TS-38)

`vize lint --cross-file` over elk, misskey, npmx.dev, nuxt-ui and reka-ui
gave 9 findings, all in misskey: 7 `justified-with-witness` and 2 recorded
as FP-3 in [ledger-fp.md](../ledger-fp.md). With FP-3 fixed, 7 findings
remain, the same 7. The P0-13 corpus shard (splitpanes,
layoutit-grid, cssgridgenerator; 130 files): no finding.

## Seeded class (TS-37)

`seed-defects.rs --html-nesting` adds the `cross-component-nesting` class to
every seeded file that has a `<script setup>` block: it imports a block
component whose root is `<div>` and renders it inside `<p>`. It expects one
`html/cross-component-nesting` finding at the usage (`<DavinciSeedBlock`),
asserted by identity together with the P4-11a classes. Recall is 100%
everywhere: the committed miniature set (`tests/tooling/davinci-html-nesting-seeds.test.ts`),
the corpus shard (3/3), and elk (17/17), misskey (76/76), npmx.dev (20/20),
nuxt-ui (79/79) and reka-ui (247/247), with nothing unexpected; see the table in
[p4-11a.md](./p4-11a.md).
