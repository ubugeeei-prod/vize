# P4-9b — Cross-file complexity rule and Doctor finding

**In progress (2026-09-22).** Both steps have landed. Slice 1 is the Patina rule on
**own** complexity. Slice 2 adds rendered (cross-file) complexity, the Doctor
hotspot finding, the facts-fed `ComplexityInput`, the curator's per-component
breakdown, and removes `logical_operator_count`. Both consumers read the facts
through the P4-1a fact group under declared demands (TS-35, see the P4-9a
record). The rule's `exact` tier is a row of the P4-6c contract table. One
dependency keeps the index box open: the render tree still reads the
analyzer's component-usage edges instead of the P4-3b identities.

## Slice 2 — rendered complexity, Doctor, curator

| subject             | decision                                                                                                                                                                                                                                                                               |
| ------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Facts in croquis_cf | `CrossFileAnalyzer` records `TemplateComplexity` (own scores, unknown, max nesting, scoped slots, every contributor with line/column) for each `.vue` source through `run_template_range`. `record_template_complexity` serves hosts that register only the script (the WASM binding). |
| Rendered            | `CrossFileResult.template_complexity`: own + Σ own over the set of components reachable through component-usage edges. A child shared by two parents and every strongly connected component count once, and `recursive` marks self-reaching components. `render_tree` lists the files. |
| `ComplexityInput`   | Template flow is fed by facts (`template_cyclomatic`, `template_cognitive`, `template_unknown`, `template_max_nesting`, `template_scoped_slot_count`). `nesting.rs` (string guard matching) and both `logical_operator_count` copies are deleted.                                      |
| Doctor              | `VIZE_DOCTOR_TEMPLATE_COMPLEXITY_HOTSPOT`: a maintainability notice when rendered cyclomatic > 106 or rendered cognitive > 139, the rendered full-corpus p95. Evidence carries own, rendered and the top three contributors. Invalidation inputs are the whole render tree.            |
| Curator             | `render_complexity_markdown` takes the component list and renders a "Template Complexity" table: own and rendered scores, the render-tree size, and where the complexity comes from (the top three contributors as `kind` Lline:col +cognitive).                                       |
| Surface churn (#23) | Analysis surface only. The JSON `ComplexityInput` fields change, `templateComplexity` is new, and a component without a template no longer receives a base cyclomatic point. The playground types, panel and the EN, JA, fr, pt-BR and zh-CN guides are updated.                       |

Measurements: the rendered law check and distribution over the full corpus
(142 projects, 40,724 components, 70,700 render edges, 695 recursive), with
its reproducing command, are in the spec. Fixtures: `cargo test -p
vize_croquis_cf --lib complexity_rendered` (shared child, direct and mutual
recursion, aliased import, contributor positions), `cargo test -p vize_curator
--lib complexity` (the markdown section snapshotted over the real pipeline),
and `cargo test -p vize_doctor --features application-analysis --test
application_complexity`. `grep -rn "logical_operator_count" crates` is empty.
Existing Doctor fixtures produce no new finding: every test render tree is
under the thresholds.
