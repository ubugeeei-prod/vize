# P4-16 — JS plugin SDK spike

**The JS plugin API shape is decided by measurement: serialized S2 visit
batches over sync napi, with fact demands declared as a static list in the
plugin manifest. One real team-convention rule runs through vitrine's napi
lane with batched visits, deterministic output, per-plugin cost in the lint
output and content-keyed results. Landed 2026-09-22; GA is P6-7.**

## Boundary

The spike covers the custom-rule hook family only (charter #29 names four;
the other three and the `@vizejs/plugin-sdk` package are P6-7). The rule sees
the neutral-core S2 page through the S1→S2 lowering directly. P4-7a's
Patina markup facade is not needed for a JS rule, which reads S2 ops and
never Patina's `MarkupRule` hooks. The persistent result cache is P5-13; the
spike keeps an opt-in in-process memo under the same content key.

## The shape

| question            | decision                                                                                                                                                                                                                                                     |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| batches vs proxies  | One JSON batch per plugin per document: the nodes of the kinds the manifest `visit`s (S2 mnemonics, page order, S2 `NodeId`s), the dense parent array, and only the demanded fact groups. One `run(batchJson) → reportsJson` call. No per-node crossing.     |
| worker vs sync napi | Sync napi on the JS thread. Rust rules keep their rayon parallelism; the JS batches run after them, outside the fused walks (a JS function is callable only on its own thread).                                                                              |
| JS-side demands     | `demands: ["templateScopes"]` in the manifest, resolved against the fact registry's group names before anything runs (an unknown name refuses exactly). One `FactManager` computes each group at most once per document, however many plugins demand it.     |
| undeclared access   | The batch never carries an undeclared group, and the SDK's `ctx.facts(name)` throws the exact TS-35-style error. `ctx.ancestors(node, kind)` throws for a kind outside `visit`.                                                                              |
| cache key           | SHA-256 over the batch schema, the plugin's name, `version` and code fingerprint (the SDK hashes every rule's source), its `visit` and `demands`, the filename and the source, each length-prefixed. Editing a rule or bumping the version is a miss.        |
| cost attribution    | `lintWithPlugins` returns `plugins[]`: per plugin `elapsedNs` (batch build + JS call + report mapping), `jsNs`, batch `nodes`/`batchBytes`, `reports`, `cached`, `contentKey`.                                                                               |
| spans               | Reports name node ids; the host anchors each on its own span (line/column computed Rust-side). Spans never cross, so a plugin cannot report a range the file lacks, and an unknown node id is an exact error.                                                |
| visible facts       | One group today, `templateScopes` (per binding-introducing op: names with their `value`/`key`/`index`/`slot` position), in a host-only registry (first fixture-range id; it never shares a manager with production groups). P6-7 exposes production α pages. |

## Measurement (release, 78 `.vue` files from `examples/`, `playground/src`, `npm/builder/vite-musea`, 50 rounds, three runs; µs per file)

`build` is the shared Rust document build (SFC split, S1, S1→S2, flatten),
paid by both arms. `sync` and `worker` are the JS side alone over recorded
batches.

| rule (shape)                                  | build | batch | proxy | sync | worker |
| --------------------------------------------- | ----: | ----: | ----: | ---: | -----: |
| `team-conventions` (`ui.for`+`ui.bind`, fact) |    64 |    88 |    86 |    7 |  20–24 |
| `design-system` (every element, one read)     |    65 |    96 |    84 |   12 |  23–37 |
| `i18n` (text + element, ancestor walks)       |    64 |   125 |   112 |   25 |  40–43 |

Batch breakdown, `design-system`: the Rust batch plus the string crossing
costs about 14 µs, `JSON.parse` about 13 µs, the rule and its report array
about 13 µs.

- **Proxies were not slower.** Per-read napi calls cost about 0.1–0.2 µs.
  On these small templates (tens of nodes) the lazy handle beat the JSON
  batch by 2–13 µs per file, 2–11 % of the whole plugin lane. The first cut
  also shipped spans in the batch; dropping them (they never need to cross)
  cut bytes by 15–19 % and moved the gap by about 3 µs.
- **Batches are chosen anyway**, on properties the proxy cannot have:
  (1) one wire format for the napi host, a worker and a WASM guest (the open
  question's "one authoring model, two runtimes"); a proxy handle cannot
  cross to either. (2) The transform-hook family must hand S2 back, so a
  serialized form exists regardless, and rules share it. (3) The batch is an
  explicit, versioned, hashable input: determinism audits and the P5-13 cache
  can hash exactly what a plugin saw, while a proxy's reads are implicit.
  (4) User code never holds a live native handle that can outlive its
  document. The cost is bounded (at most 13 µs per file here) and dominated
  by `JSON.parse`; a columnar batch (typed-array node table plus a string
  table) is P6-7's optimization, unmeasured here.
- **Sync beats worker.** The worker round trip adds 13–18 µs per file over
  sync with high variance, and buys no parallelism the pipeline needs.
