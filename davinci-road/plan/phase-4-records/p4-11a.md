# P4-11a — Content-model tables and exact per-file checker

**Acceptance evidence is complete; the box stays open until P4-6a lands.**
The contract depends on P4-6a because the `exact` tier this checker claims
has to be declared through P4-6a's precision-tier types, which have not
landed yet. When they do, registering `vue/permitted-contents` as `exact`
is the only step left.

## Boundary

`crates/vize_patina/src/html_content_model/` decides, for every element and
text node of a template as authored, whether the HTML parser keeps it where
Vue's virtual DOM puts it (parser family) and whether the content model
permits it (content-model family). The checker covers 21 classes and is
three-valued: a finding is reported only when it holds in every context
consistent with the template, and anything unknown stays silent.
`vue/permitted-contents` reports exactly what the checker proves.

## Formal (charter #36)

`formal/html-content-model` is a Lean package that sits beside `formal/impeto`. It models the checker's core and proves four things about it:

- The Kleene connectives are sound (`Tri.and_sound`, `or_sound`, `not_sound`).
- The stack-of-open-elements walk behind every scope and loop scan is sound for every concrete stack a possibly truncated chain describes (`walk_sound`). This is the walk-level form of the property the Rust differential test checks for whole verdicts by enumeration.
- A definite verdict on a truncated chain survives any ancestors the context later reveals (`walk_stable`).
- The all-dispatches verdict rule is sound for the dispatch the page really takes (`proven_sound`).

Every definition is structurally recursive, so Lean checks totality, and every verdict is decided by evaluation. The `lean` job of `.github/workflows/davinci-html-content-model.yml` builds the package and rejects proof escapes.

The model covers the walk and the verdict rule. Relating each insertion-mode rule to the spec text stays with the parse5/Chromium oracle.
