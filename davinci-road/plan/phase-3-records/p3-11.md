# P3-11 - IVM oracle

## Array-loop slice (2026-09-20)

Issue [#6251](https://github.com/ubugeeei-prod/vize/issues/6251) connects one
array-loop subset across Rust S3 lowering, independent Lean execution and
mounted VDOM/Vapor output.

`Impeto.Iteration` executes the source/alias operands using lexical JSON
environments. The second `for-key` alias is the array index; reconciliation
identity comes separately from the repeated-root key binding. Nested aliases
shadow and restore their enclosing environment.

`Impeto.Incremental` owns the previous materialized tree and a monotonically
allocated element lifetime. Updates preserve keyed or positional identities,
patch payloads, insert elements and retire removed subtrees. Its resulting tree
must equal a fresh S3 render after every update. All ordered-subset transitions
over three keys are exercised under both identity policies, with explicit
allocation and event-value expectations. The matcher's equivalence with fresh
rendering, keyed retention and exact allocation count are proved in
[P3-15](./p3-15.md); it makes no production time-complexity claim.

Three Rust-owned fixtures share their exact authored source, graph/value Folios,
scenario and complete expected tree/event/lifetime observations with the
mounted runtime. They exercise reorder, front insertion, middle deletion,
same-key object replacement, empty/refill, nested alias shadowing, cross-parent
movement and parent removal/recreation. Expected lifetime numbers are authored;
the DOM runner observes actual objects through a WeakMap, not key spelling.

The event traces exposed a production defect: the native Vapor event generator
wrapped an already transformed arrow a second time, so clicking returned a
function and delivered no event. It now uses the shared retained-AST function
classifier before choosing a wrapper, matching component-event handling.
Supplemental mounted cases cover authored arrow/function and optional-call
handlers without changing the reference fixture's expression subset.

The exact supported subset, failure boundaries and lifetime rationale are in
[`loop-reference.md`](../../../formal/impeto/fixtures/loop-reference.md).
The existing Davinci Lean workflow runs the stateful reference, Rust provenance
and mounted gates. The default Cargo suite also executes both Rust gates.

## Matrix slice (2026-09-21)

The reference now evaluates a closed JavaScript expression subset
(`Impeto.Expression`). It covers literals, lexical names, member reads,
`.length`, `!`, unary `-`, `* % + -`, relational operators, strict equality,
`&& || ?:` with JavaScript short-circuiting, and JavaScript truthiness for
`v-if`. It also evaluates `{{ }}` compound text and iterates arrays, objects
(`value, key, index`) and integer ranges (`1..n`). Anything outside the subset
fails closed. That includes calls, indexing, loose equality, division,
fractions, structured string conversion, results beyond 2^53 - 1 and objects
with array-index keys, whose JavaScript order differs from the canonical key
order. `fixtures/expression-cases.json` pins 56 supported and 31 unsupported
expressions. Lean must reproduce every supported value, and
`davinci-lean-expression.test.ts` evaluates the same supported cases with Node's
own engine.

The TS-29 matrix is generated by the Rust bridge
(`lean_reference_fixture::matrix`) as the product of:

- six sources: keyed and positional arrays, objects and ranges;
- three item bodies: non-linear text such as `item.label + ':' + item.qty * factor`,
  a per-item `v-if`/`v-else-if`/`v-else` toggle on mixed conditions, and a
  button with `:disabled`, a derived `data-id` and `record(...)` clicks;
- two wrappers: open, or a `v-if` guard that destroys and recreates the list.

Ranges have no button body, which leaves 32 cases. Each scenario patches a
non-linear parameter, reorders or rekeys the source, inserts, deletes and
patches payloads, flips toggle thresholds, closes and reopens the guard, then
empties and refills. Rust lowers every case, checks it with the validator and
commits templates, scenarios and exact graph/value Folios as JSON lines. The
Lean reference runs each scenario through the proved update machine and must
reproduce `ivm-matrix.behavior.jsonl` exactly. Every update is also compared
with a fresh render. Both mounted runtimes must then reproduce every tree,
event and actual element lifetime.

The matrix exposed one upstream defect. In `@vue/runtime-vapor`
3.6.0-beta.10, positional `createFor` blocks are updated with only the new item
(`update(block, getItem(source, i)[0])`). An unkeyed object loop therefore keeps
each reused block's old key alias after keys shift. The compiled Vapor code
reads `_for_key0.value` reactively and VDOM matches the reference. The six
`object-positional-*` Vapor traces are pinned exactly in
`ivm-matrix.vapor-gaps.jsonl`. Each entry must still differ from the reference,
and it may differ only in `data-id` spellings and identity labels, never in
structure, text, events or lifetimes. An upstream fix fails the gate until the
entry is removed. All other 26 cases, and all 32 VDOM traces, equal the
reference exactly.

## Status

_Closed 2026-09-21:_ TS-29 is green over the generated matrix. Keyed and
positional `v-for` over arrays, objects and ranges, conditional toggles and
mixed non-linear expressions reach exactly the from-scratch reference. The
equivalence of incremental and fresh rendering is proved in
[P3-15](./p3-15.md). The pinned Vapor gap is an upstream runtime defect, which
Vapor behavioral parity (TS-33) must account for.
Multi-root `<template v-for>`, destructuring aliases, string sources and
components inside loops are outside this oracle's subset. Model/IME and
supplied-slot reference semantics are covered by P3-4. P3-12 and the Phase 3
exit remain open.
