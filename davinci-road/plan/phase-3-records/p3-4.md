# P3-4 - Lean reference semantics first slice

This slice starts the P3-4 executable reference without pulling Lean into the
runtime dependency graph. The new `formal/impeto/` Lake package is pinned by
`lean-toolchain` and exercised only by the dedicated Davinci Lean workflow, in
the CI-lenient supply-chain lane allowed by charter #39.

## Contract boundary

- Input is the existing S3 Folio text contract: `phase`, `regions`, `ops`,
  `edges`, and `effects`.
- The Lean side owns a small, independent syntax model instead of importing Rust
  code or regenerated bindings.
- Fixture traces are observable semantics, not emitted-code byte shape, matching
  TS-28 and the Vapor experimental policy.

## First semantics

The first small-step machine executes the committed op sequence once under two
interpretations:

- VDOM: `insert-node` becomes `create-element`, property/event ops become patch
  events, and structural control ops become branch/list/slot observations.
- Vapor: the same S3 ops become effect-oriented observations such as
  `create-node`, `assign-prop`, `listen`, and `conditional-effect`.

Effect ids remain visible in the trace. That deliberately makes effect-scope
drift observable before optional scheduling or extraction passes land.

## Fixtures

The initial ladder covers:

- `static-text.s3.folio` - static element plus text.
- `dynamic-button.s3.folio` - prop, event, interpolation, and effect order.
- `control-flow.s3.folio` - branch-owned region and child ops.
- `rust-lowered-static-dynamic.s3.folio` - the same static/dynamic DOM surface
  emitted by `vize_s2_to_s3::lower` from a Rust parser/lowering test.
- `rust-lowered-control-slots.s3.folio` - the Rust S1->S2->S3 lowering path
  for dynamic `v-if`, slot outlet, and fallback text regions.

## Validation

- `lake build` over `formal/impeto/`.
- `lake exe impetoRef --check-fixtures`, comparing the Lean reference trace to
  the committed `.trace` files.
- `tests/tooling/davinci-lean-reference.test.ts`, keeping the fixture
  declarations and TS-28 command in sync; `davinci-lean-workflow.test.ts` pins
  the workflow and toolchain.
- `cargo test -p vize_s2_to_s3 --test lean_reference_fixture` keeps the first
  generated fixture equal to the Rust S2->S3 Folio output.

This does not close P3-4. The remaining work is to feed generated S3 fixtures
across the ladder and then compare compiled backend behavior traces against
this reference runner.

## Fourth slice (2026-09-15)

TS-28 now includes a compiled-output bridge for the two Rust-lowered ladder
fixtures. `crates/vize_atelier_vapor/tests/davinci_s3_compiled_trace.rs`
compiles each fixture through the DOM and Vapor backends, extracts backend
observation labels from the emitted render code, and compares those labels to
the committed `.vdom.trace` / `.vapor.trace` reference artifacts.

This bridge records exact fail-closed gaps instead of hiding them:
`rust-lowered-static-dynamic` Vapor currently installs the delegated listener
before the shared dynamic render effect, while the S3 reference trace orders the
dynamic prop, listener, and text effect as `assign-prop`, `listen`,
`text-effect`; `rust-lowered-control-slots` Vapor currently builds the slot
fallback before the sibling conditional block, while the S3 reference trace
orders `conditional-effect` before `slot-effect`. The test accepts only those
exact observed sequences as known gaps; every other compiled trace comparison
remains an exact reference match.

The dedicated Davinci Lean workflow also runs this cargo test, so the S3 Lean
fixtures, split backend traces, and first compiled-output trace gate now travel
together in CI.

This still does not close P3-4. The remaining step is to replace the emitted
code observation bridge with mounted runtime behavior traces and compare those
scripted traces against the same backend-specific reference contract.

## Fifth slice (2026-09-15)

The TS-28 compiled bridge now executes the emitted DOM and Vapor render
functions instead of deriving observations only from source-code positions.
`tests/tooling/support/davinci-runtime-trace.mjs` provides a deterministic JS
host runner: the VDOM path materializes the returned VNode tree and walks it in
mount order, while the Vapor path executes template factories, render effects,
slot/branch factories, and delegated listener assignments through traceable
helper stubs. The Rust cargo gate feeds compiler output into that runner and
compares the executed trace labels to the same `.vdom.trace` / `.vapor.trace`
reference artifacts.

The exact Vapor runtime gaps from the fourth slice remain fail-closed: delegated
listener assignment is still observed before the shared dynamic render effect,
and the slot fallback is still observed before the sibling conditional block.
Those are now runtime-trace gaps rather than emitted-code-order gaps.

This still does not close P3-4. The remaining step is to replace the
deterministic helper host with mounted DOM/Vapor behavior traces from the
Behavioral runner, using the same backend-specific reference contract.

## Seventh slice (2026-09-16)

The dynamic-button fixture now connects those two evidence lanes. Its graph
and value Folios are checked byte-for-byte against Rust S1->S2->S3 lowering.
`Impeto.Values` independently parses all 18 operand roles and six value kinds
using Lean's JSON parser, including escaped text and reference-shape checks.
`Impeto.Observation` interprets supported native elements, literal attributes,
identifier-valued interpolation, boolean disabled bindings and click handlers.
`Impeto.Behavior` applies the same `.scenario.json` consumed by the actual
mounted Vue DOM/Vapor test and compares the entire `.behavior.json` artifact.

The ten observations cover mount, reactive patches through string/null/integer/
boolean/escaped Unicode text, two click deliveries, and empty-tree unmount.
No operation-order exception or projected subset is used for this comparison.
Both reference and mounted gates were verified to fail when the expected
observation was deliberately corrupted, before restoring the correct fixture.
The Lean command also runs 108 role/kind parser combinations and negative
witnesses for malformed rows, ownership, missing/duplicate operands, unsupported
expressions, handlers, phases, state values and interaction steps.

This is a deliberately bounded executable semantics, not a JavaScript evaluator
or a proof about scheduling. The interpreter fails closed outside its supported
HTML/attribute/property subset; expressions are literal values or direct context
identifiers, displayed numbers are signed 32-bit integers, and clicks require
one enabled button with one `save` handler. Opaque, foreign and filter operands
are preserved by parsing but never interpreted as JavaScript. Control/slot/list/
model semantics, disabled interactions, arbitrary expressions, broader mounted
fixtures and Lean theorems remain open. P3-4 and P3-12 are not complete.

## Eighth slice (2026-09-16)

The shared dynamic-button scenario now distinguishes native HTML button
activation (`activate: "button"`, executed with `click()`) from synthetic
`dispatchEvent` steps. Its twelve full observations include activation while
initially disabled, activation after enabling, an ordinary dispatched click,
and activation after disabling again. Disabled activation preserves both the
tree and the event history; enabled activation delivers exactly one `save`
when the button has that handler. Handler-free buttons complete activation and
enabled synthetic dispatch without recording events, in both the Lean reference
and the compiled DOM/Vapor trace; multiple or invalid handlers remain rejected.

Both mounted backends and the independent Lean reference match the same
artifact. An intentionally added event after disabled activation was rejected
by both gates before the correct artifact was restored. Invalid activation
fields/selectors and zero or multiple mounted targets fail closed. Synthetic
dispatch on disabled controls remains outside the Lean subset; its semantics
are not silently changed into activation semantics. This is not evidence for
trusted pointer events, keyboard activation, focus management, other controls,
or completion of P3-4/P3-12.

## Ninth slice (2026-09-18)

The Rust-lowered control/slot fixture now uses one authored template file in
the S3 provenance, compiled-label and mounted-runtime gates. This also removes
the former self-closing versus explicit-end-tag input difference. Rust checks
the exact graph and value Folios, including the updated source spans.

The independent Lean interpreter selects the first matching boolean-identifier
condition, supports a final unconditional else, renders an absent slot's
literal-name fallback, and applies targeted `v-text` to its owning element.
Branch operands must name every owned region exactly once in authored order.
Malformed ownership, missing/duplicate operands, unsupported slot props/names,
invalid binding targets and ambiguous text bindings fail closed. Supplied slots,
compound expressions and non-boolean conditions are outside this executable
subset, rather than approximated as successful rendering.
Static tags, namespaces, attributes, binding shapes and expression syntax are
validated even in inactive branches. State lookups remain lazy: a supported
identifier in an inactive branch need not exist in the current context.

Both mounted Vue backends and Lean compare the complete same ten-observation
artifact: mount, simultaneous condition/fallback updates, repeated hide/show,
string/null/integer/boolean/escaped Unicode text and empty-tree unmount. A
deliberately corrupted initial element was rejected by both executable gates
before the expected artifact was restored. Lean also tests branch priority,
short-circuiting, else order and no-match behavior.

Interaction targets now come from the visible rendered regions, not all
button operations in the graph. Lean rejects hidden or ambiguous buttons.
The associated nested-listener compiler regression is tracked separately
in #6202 rather than hidden behind an operation-label exception.

Both Rust-lowered template fixtures now have full stateful reference equality.
Keyed lists, supplied slots, native model/IME reference semantics, arbitrary
JavaScript and scheduling theorems remain open. P3-4/P3-12 and the production
lane are not complete.

## Native model slice (2026-09-22)

`Impeto.Model` gives S3 `ui.model` bindings (`set-prop` with binding kind
`model`) an independent reference semantics, written from Vue's directive
contract. It covers text inputs, including IME composition gating, `.lazy`,
`.trim`, `.number` with `looseToNumber` and the `/^0\d/` exception;
checkboxes over booleans and arrays (`looseIndexOf` plus first-match
`splice`); radios, which resync only when the model changes; and single,
multiple and `.number` selects, whose resync is suppressed while the select
itself assigns. Live DOM state (`value`, `checked`, per-option `selected`,
`composing`) is keyed by the proved update machine's element identity. The
mounted hook creates it and update hooks change it only when a reactive write
changes a value (`Object.is`). Events mutate it exactly as the mounted runner's
`event` steps do. Model paths may be identifiers or member paths assigned in
place. Textareas, dynamic options, `true-value`/`false-value`, controls inside
loops and fractional numbers fail closed.

`model-reference.*.jsonl` holds twelve Rust-lowered cases: IME/text,
`.lazy`, `.trim`, `.trim.number`, checkbox arrays and booleans, a radio pair,
single, multiple and numeric selects, a member path, and a control that `v-if`
destroys and recreates. Rust checks the graph/value Folios. Lean computes every
observation, including live form properties, and `davinci_mounted_behavior::models`
requires the compiled DOM and Vapor output to match them exactly. Both runtimes
matched on the first run. `Impeto.ModelTests` rejects 18 out-of-contract
scenarios and operand damages.

P3-4 stays open until supplied slots use the same reference contract.
