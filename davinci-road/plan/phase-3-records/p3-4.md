# P3-4 - Lean reference semantics first slice

This slice starts the P3-4 executable reference without pulling Lean into the
runtime dependency graph. The new `formal/impeto/` Lake package is pinned by
`lean-toolchain` and exercised only by the dedicated Davinci Lean workflow, in
the CI-lenient supply-chain lane allowed by charter #39.

## Contract boundary

- Input is the existing S3 Folio text contract: `phase`, `regions`, `ops`,
  `edges`, and `effects`.
- The Lean side owns a small, independent syntax model instead of importing Rust
  code or regenerated bindings.
- Fixture traces are observable semantics, not emitted-code byte shape, matching
  TS-28 and the Vapor experimental policy.

## First semantics

The first small-step machine executes the committed op sequence once under two
interpretations:

- VDOM: `insert-node` becomes `create-element`, property/event ops become patch
  events, and structural control ops become branch/list/slot observations.
- Vapor: the same S3 ops become effect-oriented observations such as
  `create-node`, `assign-prop`, `listen`, and `conditional-effect`.

Effect ids remain visible in the trace. That deliberately makes effect-scope
drift observable before optional scheduling or extraction passes land.

## Fixtures

The initial ladder covers:

- `static-text.s3.folio` - static element plus text.
- `dynamic-button.s3.folio` - prop, event, interpolation, and effect order.
- `control-flow.s3.folio` - branch-owned region and child ops.
- `rust-lowered-static-dynamic.s3.folio` - the same static/dynamic DOM surface
  emitted by `vize_s2_to_s3::lower` from a Rust parser/lowering test.
- `rust-lowered-control-slots.s3.folio` - the Rust S1->S2->S3 lowering path
  for dynamic `v-if`, slot outlet, and fallback text regions.

## Validation

- `lake build` over `formal/impeto/`.
- `lake exe impetoRef --check-fixtures`, comparing the Lean reference trace to
  the committed `.trace` files.
- `tests/tooling/davinci-lean-reference.test.ts`, keeping the workflow, pinned
  toolchain, fixture declarations, and TS-28 command in sync.
- `cargo test -p vize_s2_to_s3 --test lean_reference_fixture` keeps the first
  generated fixture equal to the Rust S2->S3 Folio output.

This does not close P3-4. The remaining work is to feed generated S3 fixtures
across the ladder and then compare compiled backend behavior traces against
this reference runner.

## Second slice (2026-09-14)

The Rust-lowered fixture bridge now covers both the static/dynamic element
case and a control/slot fallback case. `lean_reference_fixture.rs` checks both
Folio texts directly against `vize_s2_to_s3::lower`, while the Lean runner
checks each paired `.trace` through `impetoRef --check-fixtures`.

P3-4 still remains open until compiled backend behavior traces are compared
against the Lean reference instead of only comparing S3 reference traces.

## Third slice (2026-09-15)

The TS-28 fixture ladder now carries backend-specific trace artifacts beside
the combined reference trace:

- `.vdom.trace` records the VDOM interpretation for each S3 folio.
- `.vapor.trace` records the Vapor interpretation for each S3 folio.

`impetoRef --check-backend-fixtures` verifies those split traces in the Lean
lane, while `vize_impeto::trace` mirrors the same backend observation labels
for ordinary Rust tests. The Rust S2->S3 bridge now proves both generated folio
text and backend-specific trace text for the rust-lowered fixtures.

This still does not close P3-4. The next remaining step is to feed traces
captured from compiled DOM/Vapor outputs into the same backend-specific fixture
contract.

## Fourth slice (2026-09-15)

TS-28 now includes a compiled-output bridge for the two Rust-lowered ladder
fixtures. `crates/vize_atelier_vapor/tests/davinci_s3_compiled_trace.rs`
compiles each fixture through the DOM and Vapor backends, extracts backend
observation labels from the emitted render code, and compares those labels to
the committed `.vdom.trace` / `.vapor.trace` reference artifacts.

This bridge records exact fail-closed gaps instead of hiding them:
`rust-lowered-static-dynamic` Vapor currently installs the delegated listener
before the shared dynamic render effect, while the S3 reference trace orders the
dynamic prop, listener, and text effect as `assign-prop`, `listen`,
`text-effect`; `rust-lowered-control-slots` Vapor currently builds the slot
fallback before the sibling conditional block, while the S3 reference trace
orders `conditional-effect` before `slot-effect`. The test accepts only those
exact observed sequences as known gaps; every other compiled trace comparison
remains an exact reference match.

The dedicated Davinci Lean workflow also runs this cargo test, so the S3 Lean
fixtures, split backend traces, and first compiled-output trace gate now travel
together in CI.

This still does not close P3-4. The remaining step is to replace the emitted
code observation bridge with mounted runtime behavior traces and compare those
scripted traces against the same backend-specific reference contract.

## Fifth slice (2026-09-15)

The TS-28 compiled bridge now executes the emitted DOM and Vapor render
functions instead of deriving observations only from source-code positions.
`tests/tooling/support/davinci-runtime-trace.mjs` provides a deterministic JS
host runner: the VDOM path materializes the returned VNode tree and walks it in
mount order, while the Vapor path executes template factories, render effects,
slot/branch factories, and delegated listener assignments through traceable
helper stubs. The Rust cargo gate feeds compiler output into that runner and
compares the executed trace labels to the same `.vdom.trace` / `.vapor.trace`
reference artifacts.

The exact Vapor runtime gaps from the fourth slice remain fail-closed: delegated
listener assignment is still observed before the shared dynamic render effect,
and the slot fallback is still observed before the sibling conditional block.
Those are now runtime-trace gaps rather than emitted-code-order gaps.

This still does not close P3-4. The remaining step is to replace the
deterministic helper host with mounted DOM/Vapor behavior traces from the
Behavioral runner, using the same backend-specific reference contract.
