# P5-4a — Salsa resident database skeleton

Contract: [phase-5-tasks.md](../phase-5-tasks.md#p5-4a--salsa-resident-database-skeleton).
Landed 2026-09-22.

## What landed

`crates/vize_resident/` (`publish = false`, experimental) is the resident
tier's salsa database — the charter #10 two-tier split made concrete. Three
modules:

- **`artifact`** — the owned per-block artifacts and the pure stage
  functions that compute them: `split_blocks` (S0: the SFC descriptor's
  blocks, each with its P5-1a `source_block_key`), `surface_artifact` (S1:
  the `SurfacePage` key plus the tokenizer findings), `page_artifact` (S2:
  the owned `S2Folio`, its page key, and the lowering diagnostics; template
  blocks through `lower_with_caps`, style blocks through
  `lower_style_block`). Every function reads a `BlockSource` — content,
  never position — so every artifact is block-relative. These functions are
  also the clean path: `compute_file_artifacts` is what TS-42 compares the
  tier with.
- **`db`** — `ResidentDatabase`. Inputs: `SourceFile { path, text }`
  (`Durability::LOW`, an open buffer) and the singleton `ProjectConfig`
  (`Durability::HIGH`). Queries: `sfc_blocks(file)` → `s1_block(block)` /
  `s2_page(block)`.
- **`accounting`** — per-query `executed` / `reused` counts taken from
  salsa's own event stream (`WillExecute`, `DidValidateMemoizedValue`), so
  the TS-46 accounting cannot disagree with what the engine did.

## The firewall

`sfc_blocks` re-runs on every keystroke but only re-creates the file's
`Block` tracked structs. A block's identity is `(file, kind, ordinal)`; its
content (`BlockSource`, carrying the S0 key) and its position (`start`, the
S0 side table) are separate `#[tracked]` fields. Salsa compares each
re-created field with its previous value and bumps only the changed ones, so:

- an edit inside one block changes that block's `source` alone — every other
  block's `s1_block` / `s2_page` memo is reused without running;
- an edit above a block moves only its `start`, which no stage query reads —
  the P5-1a span-relative keys are what make this sound, because the served
  artifacts carry block-relative spans.

## Measured (the `firewall` test, counters pinned exactly)

Fixture: `script setup`, template, two styles. Each scenario reads every
artifact through the queries, asserts equality with `compute_file_artifacts`
run from scratch, then pins the complete accounting:

| Scenario                                | `sfc_blocks` | `s1_block` exec/reused | `s2_page` exec/reused |
| --------------------------------------- | ------------ | ---------------------- | --------------------- |
| first read                              | 1 / 0        | 4 / 0                  | 4 / 0                 |
| repeat read, same revision              | 0 / 0        | 0 / 0                  | 0 / 0                 |
| edit inside the template                | 1 / 0        | 1 / 3                  | 1 / 3                 |
| edit inside the second style            | 1 / 0        | 1 / 3                  | 1 / 3                 |
| edit inside the script (above the rest) | 1 / 0        | 1 / 3                  | 1 / 3                 |
| insert above every block                | 1 / 0        | 0 / 4                  | 0 / 4                 |
| no-op edit (same text)                  | 1 / 0        | 0 / 4                  | 0 / 4                 |
| project config change (Vue 2)           | 0 / 1        | 0 / 4                  | 4 / 0                 |

Every block runs both per-block queries (`s1_block` answers `None` outside a
template), so "only the edited block" is exactly one execution per query.
The config row shows durability doing its job: the HIGH-durability change
re-validates the LOW-durability split instead of re-running it, and only the
queries that read the config re-execute.

## Dependency admission (charter #39)

- The workspace pins `salsa` at `=0.28.4` with default features off and
  only `macros` and `inventory` on; `rayon` stays off (file-parallelism is
  the caller's, charter #33). New lockfile crates:
  `salsa`, `salsa-macros`, `salsa-macro-rules`, `boxcar`,
  `crossbeam-queue`, `foldhash`, `hashlink`, `intrusive-collections`,
  `inventory`, `portable-atomic`, `thin-vec`, `typeid`.
- `cargo audit --deny warnings` is clean against the local advisory
  database (2026-08-27); CI's `security-audit` job runs it against a fresh
  one on every PR.
- `tests/tooling/davinci-resident-salsa.test.ts`: only `vize_resident`
  names `salsa` (and the check reports `vize_atelier_sfc` when an edge is
  injected there); the pin and features are exact; the crate is unpublished;
  and `cargo tree -p vize --no-default-features` — the one-shot binary —
  lists neither `salsa*` nor `vize_resident` (scope proof: the listing
  contains `vize`, `vize_atelier_sfc` and `vize_s1_to_s2`).
- The shared `Recorder` behind the event callback is the crate's one
  `Arc`, allowed locally with its reason: salsa clones the database handle
  per snapshot, and the callback lives in the storage.
