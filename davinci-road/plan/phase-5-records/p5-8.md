# P5-8 — Corsa session reuse

Contract: [phase-5-tasks-later.md](../phase-5-tasks-later.md#p5-8--corsa-session-reuse).
Landed 2026-09-22. Step 1 (the key) is already on this branch; this slice is

## The key

`CorsaSessionKey` is the P5-1b `corsa.session` fingerprint. `SessionInputs`
resolves exactly that row's six inputs, and the fold refuses a missing or an
extra one. `every_manifest_input_separates_sessions` flips each input and
asserts the seven keys are pairwise distinct.

## The map

`vize check-server` is a thin CLI over `vize_canon::CorsaServer`. The server
no longer keeps one path-keyed client. `SessionMap` holds one
`CorsaProjectClient` per fingerprint:

- a miss spawns the session;
- a hit reuses it;
- a session idle for `--idle-timeout-secs` (default 60; `0` keeps it until
  the process exits) is dropped, and the next check spawns again.

The key is recomputed on every check: the nearest `tsconfig.json` at or under
the server's project root, `corsa_build_identity` of the executable that
session will run, and the request's canonical flag spelling (`vize check`
sends none). A different tsconfig's bytes, or a different flag spelling, is
a different slot — the old session stays until idle teardown, it is not
reused.

TypeScript project initialization is counted where it happens:
`ProjectSession::spawn` and a successful editor-LSP `initialize`. The server
samples that counter around each check. `session-stats` reports
`projectInits` and `liveSessions`.

## Evidence

The second run is an init counter, not a timer.

- `the_second_check_does_not_initialize_and_a_new_tsconfig_does`: the first
  check initializes (`projectInits >= 1`, one live session) and reports
  `TS2322` at line 2, column 7. The second check of the same file reports
  the same diagnostics and does not move the counter. Rewriting the tsconfig
  (`strict` true → false) opens a second live session and initializes again;
  the check after that reuses the new key.
- `feature_flags_do_not_share_a_session_and_each_flag_set_is_reused`: `""`
  and `options-api=0` are two live sessions. Checking either again does not
  initialize.
- `an_idle_session_is_torn_down_and_the_next_check_initializes`: reaping past
  the idle window drops the session; the next check initializes.
- `check_diagnostics_match_with_and_without_the_server_and_the_second_run_does_not_init`
  runs `vize check src/App.vue --format json` and the same command through
  `vize check --socket`. Both, and a second socket run, report exactly
  `error:2:7 [TS2322] Type 'number' is not assignable to type 'string'.`
  with `errorCount` 1 and `warningCount` 0. `session-stats` is
  `{projectInits: 0, liveSessions: 0}` before the first check, then
  `projectInits >= 1` and `liveSessions` 1, and the second check leaves both
  numbers unchanged. The server applies `vize check`'s reportability policy,
  so an unrequested `TS6133` is not part of that oracle.
