# P2-18 — Spolvero feed v1

**The observer's folio output as a consumable, schema-versioned feed,
plumbed into the inspector payloads. Landed 2026-08-21; the rendering half
of "the playground shows the stage ladder" is the marked review point below,
not a claim this record makes.**

## The feed is a serialization of `FolioDump`, never a second collector

The contract said "build on P2-13's machinery, not duplicate it", and the
shape of that is: `FolioDump` stays the only thing that decides which pages
exist (emission order, the `--folio-after-change` hash gate), and the new
`SpolveroFeed` (`crates/vize_davinci/src/folio/feed.rs`) is a _serialization_
of that collection — `SpolveroFeed::of_dump` copies the dump's pages
verbatim. To carry provenance without re-parsing file names, `DumpPage`
gained `stage`/`pass` fields recorded at `after_pass` time from the
`PassEvent`; its `name` remains the derived-and-cached file name, computed
once at emission where the sequence number is known (noted against the
P2-17 redundancy rule: single writer, cache at the only site that knows
`seq`).

The document is `{schema_version, command, pages[{path, stage, pass,
text}]}` — committed at
[`spolvero-feed.schema.json`](../spolvero-feed.schema.json), `schema_version`
a `const 1` the printer emits from the module constant so a value cannot
carry a version its shape does not have. Two deliberate divergences from the
P0-11 export header:

- **No `tool`/`tool_version`.** devtool.md's negotiation requirement is
  `schema_version`; a tool version embedded in the inspector payload would
  rot every byte-exact payload pin on every release. `command` (the
  producing surface: `davinci-opt`, `inspector`, `analyze-sfc`) is kept for
  provenance.
- **The serializer is hand-written** (`to_json` + a minimal RFC 8259
  escaper), because `vize_davinci` is `no_std + alloc` with no serde and the
  P2-14 boundary audit should not widen for a feed. It is the shape's
  **only** serializer: every other surface embeds the parsed value of this
  output. The escaping law (output parses back to exactly the input text)
  is pinned in TS-52.

`davinci-opt --folio-dir` now writes `spolvero.json` beside the pages, from
the same `FolioDump` the pages came from — directory and feed cannot
disagree. A fully hash-gated run writes a feed with **zero pages**: the
P2-13 "vacuity is observable" property upgraded from an empty directory to
an explicit statement (`davinci_opt_dumps` pins the listing, TS-52 pins the
content).

## The inspector integration, and where S1/S2 pages come from

- **`InspectorPayload`** (`vize_curator`) gains a `spolvero` member:
  `build_payload` builds S1 pages for every parseable `.vue` file with a
  template and embeds the feed. The S1 page is produced by parsing the
  template into `vize_sinopia`'s lossless surface tree and rendering it back
  (`stage: "s1"`, `pass: "parse"` — a parse product, not a pass product; the
  schema documents `pass` as "producing step"). By TS-19's fidelity law the
  text equals the authored template bytes — proven through the tree, never
  copied from the source; TS-52 asserts that equality on well-formed _and_
  malformed templates.
- **The wasm `analyzeSfc` result** gains a top-level `spolvero` sibling of
  the alias keys, same shape, `command: "analyze-sfc"`, built from the
  already-parsed descriptor (no re-parse on the playground path).
- **S2 pages: none, honestly.** Nothing lowers into `vize_disegno` until
  P2-8, so no surface can produce an S2 page today. The feed is
  stage-agnostic — S2 pages join by pushing pages, with no schema change —
  and this record says the ladder currently has rungs S1 (and croquis via
  the alias), not S2.

**The croquis alias was left byte-untouched and is now pinned.** The stage
pages live in the sibling `spolvero` key, _not_ inside the `folio` alias
object, so `vir` and `folio.croquis` keep their exact bytes structurally.
No test had ever pinned the alias; `vize_vitrine::wasm::tests_spolvero` now
pins both keys against a committed 1665-byte croquis folio literal, their
equality, and the alias object's exact shape.

## Deviations and recorded constraints

- **`vize build --folio-dir` still writes no feed.** The build path has no
  `FolioDump` until P2-12b, and P2-13 pinned "directory created, zero
  pages" (`the_build_folio_dir_is_created_and_stays_empty_until_p2_12b`,
  still green). The feed follows the dump; P2-12b inherits both.
- **The payload's embedded feed serializes with alphabetized keys** (it
  rides as a parsed `serde_json::Value` inside a serde payload). Canonical
  bytes remain `SpolveroFeed::to_json`'s; schema validation is key-order
  blind. Recorded so nobody pins the embedded form as "the" byte shape.
- **Share-URL growth.** Payload-embedded S1 pages roughly duplicate
  template bytes in `--format url` output. Accepted for v1 — the inspector
  already warns at 7000 bytes, and in-band-vs-out-of-band is exactly the
  P2-19 transport question this task must not pre-decide.
- **The playground UI is untouched** (zero TS files changed, so its suites
  are unaffected by construction; `decodeInspectorPayload` passes unknown
  members through by code inspection). The wasm result now carries
  everything a ladder view needs — but no view renders `spolvero` yet.
  That is the review point, marked, not dressed as a gate.
- The feed's page list is a stage-dump channel: files that are not `.vue`,
  fail SFC parsing, or lack a template contribute no page (pinned).
  Diagnostics stay on their own surfaces.

## Review point — what was verified locally vs what needs eyes

Verified locally (machine-checked, in TS-52 and the updated suites): the
feed's exact content on every producing surface, schema validity, the
S1 fidelity equality, and the alias byte-identity. Verified by code
inspection only: `decodeInspectorPayload` tolerates the new member (its
guard checks `version` and `files`, nothing else). **Needs eyes:** the
playground actually _showing_ the stage ladder for a compiled SFC — no CI
job evaluates a rendering claim, and no ladder view exists yet; the
payload plumbing is the deliverable this task makes true.
